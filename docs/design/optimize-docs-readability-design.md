# `optimize-docs-readability` 设计说明

> 本文面向要修改 `optimize-docs-readability` 的维护者，解释其判据、范围、输出和设计取舍。运行时行为以 [SKILL.md](../../skills/optimize-docs-readability/SKILL.md) 和 [报告模板](../../skills/optimize-docs-readability/references/report-template.md) 为准；本文是该 Skill 的权威设计说明，不作为安装包的运行依赖。
>
> 全仓库文档缺口与导航盘点见 [`audit-docs-landscape` 设计](./audit-docs-landscape-design.md)。两份设计各自维护所属 Skill；共同术语沿用根 `CONTEXT.md`。
>
> **按需要读**：修改 `SKILL.md` 看第 7–11 节和第 14 节；了解判据依据看第 7.1、12、16 节；查验证记录看第 13 节，查决策出处看第 15 节。第 14.1 节约束设计维护者，第 14.2 节约束 Skill 的运行时行为。

## 1. 一句话定位

`optimize-docs-readability` 回答：**这篇文档让真人读者在哪里卡住？**

独立审阅时，Skill 产出 findings 和具体改写建议，保持被审查文档只读；写作任务中，Skill 在长文交付前检查并优化本轮获授权的草稿，范围见第 9.1 节。

本文用 **Viewer** 指调用 Skill 并阅读其 findings 的人，用 **Reader** 指被审查文档的读者，两者不可互换；完整辨析见第 6 节。

## 2. 要解决的核心问题与背景

Viewer 在 2026-09-03 明确了三个痛点及其重要等级 `#2 > #3 > #1`。编号沿用 Viewer 当时的列举顺序，不表示优先级；下表按重要等级从高到低排列：

| 原始编号 | 痛点 | 归属 |
| --- | --- | --- |
| #2 | 单篇文档本身难读——结构混乱、术语没解释、把教程和参考手册混在一起 | `optimize-docs-readability` |
| #3 | 该有的文档根本不存在——没有架构说明、没有"为什么这么设计"的记录 | `audit-docs-landscape` |
| #1 | 入口和导航——新人不知道该读哪篇、从哪开始，文档之间没有路径 | `audit-docs-landscape` |

生态调研结论（同日）：`#2` 在 skills 生态里是真空，没有可信的文档审查型 Skill；`#3` 和 `#1` 也没有。本机既有 Skill 覆盖的是**撰写**（`codebase-documenter`）、**漂移检测**（`neat-freak`）和**规格逆向**（`spec-miner`），没有任何一个从真人读者视角审查既有文档。

本 Skill 承接痛点 #2；痛点 #3 与 #1 的设计由 [`audit-docs-landscape` 设计](./audit-docs-landscape-design.md) 承载。

## 3. 设计目标

1. 缺陷判定有单一原理可依，判据既能被派生也能被拒绝，而不是一份只能累积的清单。
2. 审查结论必须能追溯到"这篇给谁看、要他达成什么"，而不是通用写作风格偏好。
3. 每条 finding 必须说得出一个真人读者具体损失了什么；主题本身难导致的费力不报。
4. 逐篇审查（高频、范围小）与全仓库盘点（低频、范围大）不互相拖累。
5. 独立审阅产出可以直接交给既有 Skill 落地，不留悬空待办。
6. 不与第 5 节列出的既有 Skill 职责重叠。
7. 判据全部由 `SKILL.md` 承载；未证明需要前不引入脚本和测试。

## 4. 明确非目标

本 Skill 不提供：

- 在独立审阅中修改被审查文档，或修改任务范围外的文件；
- 撰写新文档（`codebase-documenter`）；
- 文档与代码行为的语义一致性对账（`neat-freak`）；
- 从代码逆向生成规格或 API 文档（`spec-miner`）；
- 判断需求、计划、spec 或设计方案是否成立、完整、可行（`ce-doc-review`）；这些文档的文字可读性仍可由 `optimize-docs-readability` 审查；
- 建立领域词汇表或 ADR（`domain-modeling`）；
- 面向 agent 的指令文件的可读性优化（见第 8.2 节）；
- 代码注释、docstring、标识符命名的审查——那是代码内文档，不是本文对象；
- 文档站点的构建、发布或链接可达性的网络校验；单篇图表的渲染核对见第 11.1 节。

## 5. 与既有 Skill 的边界

| Skill | 它做的 | 与本 Skill 的分界 |
| --- | --- | --- |
| `codebase-documenter` | 撰写 README、架构文档、API 文档、注释 | 它负责撰写；可在交付长文前调用第 9.1 节的可读性优化。独立审阅的 finding 仍可作为它的输入 |
| `neat-freak` | 让文档、规则文件、agent memory 与代码和运行时的实际行为对齐 | 它查**语义是否与代码相符**；我们查**读者照着这篇能否走通**（见第 9.2 节判据 7） |
| `spec-miner` | 从既有代码逆向出规格、依赖图、API 文档 | 它生产内容；`audit-docs-landscape` 只指出缺口并把它派给 `spec-miner` |
| `ce-doc-review` | 用角色视角审查需求、计划、spec 和设计方案的正确性、完整性与可行性 | 按审查目标分工：它审要求和方案是否成立，`optimize-docs-readability` 审文字是否让 Reader 读懂。同一篇设计文档可以分别接受两种审查；可读性通过不代表方案通过 |
| `domain-modeling` | 建立 `CONTEXT.md` 和 `docs/adr/` | 它是 `audit-docs-landscape` 对"决策理由缺失"这类 finding 的指定归属 |
| `codebase-design` | 让模块对 AI 可导航 | 目标读者不同：它优化 AI 可导航性，我们优化真人可读性。冲突时本文范围内以真人读者为准 |

与 `audit-docs-landscape` 的分工见第 7.1 节；它的具体探针和导航规则见 [`audit-docs-landscape` 设计](./audit-docs-landscape-design.md)。

## 6. 领域语言

本设计的术语是根 [`CONTEXT.md`](../../CONTEXT.md) 的 topic `Documentation Readability`，不新建 context 文件。

该 topic 定义：Repository documentation、Reader、Purpose、Purpose confusion、Reader-transferred work、Intrinsic difficulty、Reader loss、Documentation gap、Orphan document、Doc landscape、Agent-directed file、两个 Skill 名，以及这两份设计的合称（Documentation Readability design）。术语定义与 `_Avoid_` 别名以 `CONTEXT.md` 为准，本文不重复。

三点属于审查流程细节而非词汇表内容，记在这里：

- 四种 Purpose 取自 Diátaxis：`TUTORIAL`（带着走一遍）、`HOW-TO`（完成一个具体任务）、`REFERENCE`（查一个事实）、`EXPLANATION`（理解为什么）。
- Purpose confusion 之所以是问题，是因为不同 Purpose 的阅读模式相反——`TUTORIAL` 要顺序读，`REFERENCE` 要跳读——混在一篇里两类 Reader 都被拖累。
- **Viewer**：调用这两个 Skill、并阅读其 findings 的人。它不是 `CONTEXT.md` 的术语。与 Reader 必须分清——Reader 是被审查文档的读者，Viewer 是审查输出的读者。

## 7. 判定基础

### 7.1 判定缺陷的统一原理：Reader-transferred work

**一处文档缺陷，就是作者把本该自己做的工作转移给了 Reader。** 这是本设计判定缺陷的唯一原理，第 9.2 节的每条判据都必须由它派生。

学理支撑三层：

- **外在认知负荷**（Sweller，认知负荷理论）——被转移的工作正是由呈现方式而非主题本身造成的负荷。这一层同时给出了排除规则，见下文。
- **知识的诅咒**（Pinker《The Sense of Style》，概念源自 Camerer/Loewenstein/Weber）——解释了作者为什么察觉不到自己转移了工作：他无法把已知的东西重新变成未知。这也是这件事必须由外部审查者做、以及第 7.2 节的读者判定必须排在最前的原因。
- **Diátaxis**（Procida）——退化为本原理在文档集层面的一个特例：目的混杂转移的是"过滤掉不属于我的内容"这份工作。

本设计借 Given-New 契约（Clark & Haviland）解释判据 4、5 所关注的理解负担，借最小化指导（Carroll《The Nurnberg Funnel》）支持判据 7 的任务导向检查。理论与具体规则的对应及推导边界见第 16 节。

这条原理立刻带来四件事：

**1. 判据的准入测试。** 任何判据必须能写成"Reader 被迫做 X，而作者本可以做掉 X"。写不出来的是口味，不进 `SKILL.md`。这使判据可以被**拒绝**，而不是只能累积。

**2. Intrinsic difficulty 不是缺陷。** 主题本身难导致的费力不计入。讲分布式共识的文档难读，是因为共识难。这条排除规则是长文档审查不产出成批误报的关键。

**3. Reader loss 是定义而不是过滤器。** 说不出被转移的是哪份工作，就不存在缺陷。它不是钉在判据列表后面的补丁。

**4. 它决定了两个 Skill 对内容问题的分工。** 作者掌握着该信息、但文档让 Reader 自己找回来 → `optimize-docs-readability`；该信息从来没被写在任何地方 → `audit-docs-landscape`的 Documentation gap。内容问题的触发歧义以此为准；跨篇导航始终由 `audit-docs-landscape` 检查，包括信息已写下但从入口找不到的情况。

原理的滥用风险要锁住：**"Reader 需要思考"不等于工作被转移。** 审查者必须根据原文和 Reader/Purpose 指出作者本可以消除的具体工作，包括还原作者已有的信息，或筛掉无关表达、辨别重复内容是否另有含义。理解文档所必需的信息从未被写下时，沿用 `audit-docs-landscape` 的缺口处理。

### 7.2 为什么读者与目的判定必须是第一步

参照来源 `streamlit/streamlit@reviewing-readability`（下称参照 Skill）能固定单一读者画像（"正在读这段代码的开发者"），因为代码注释的读者只有一种。**仓库文档不是这样**：README 的 Reader 是"在评估要不要用这个项目的人"，CONTRIBUTING 的 Reader 是"想提 PR 的人"，架构文档的 Reader 是"要改这块代码的人"。套一个固定画像会让审查退化成抠字眼。

更重要的是：**判断"这一段该不该在这篇里"唯一的依据就是 Reader 是谁、要达成什么。** 没有这一步，判据 2 到 4 全部无法执行，只剩下语法和风格可挑。

顺序固定为 Reader → Purpose → 内容判断，不可颠倒。

### 7.3 自动推定的证据来源

Viewer 在 2026-09-03 选择**自动推定**而不是每篇都问。`optimize-docs-readability` 先采用用户在当前任务中的明确意图及后续澄清；需要自动推定的部分按以下文档证据排序。`audit-docs-landscape` 盘点既有文档时也沿用这个文档证据顺序：

1. **文档自己的声明**——标题、前言、"本文面向…"这类句子。
2. **文档在仓库中的位置和文件名**——`README.md`、`CONTRIBUTING.md`、`docs/adr/`、`docs/agents/` 各自有约定读者。
3. **谁链接到它、用什么措辞链接**——上游文档的引导语通常直接说明了读者处境。
4. **代码的实际形态**——文档描述的是对外契约还是内部机制，决定了 Reader 是使用者还是维护者。

独立审阅时，推定结果必须在输出中显式列出，并标注依据的是明确请求或上面哪条文档证据。写作收尾时，agent 先使用写作请求明确的 Reader/Purpose，再用草稿中的证据补足；判定用于优化正文，不额外交付判定表。依据同一证据确定要回答的问题及所需细节层级；连续编辑时，先区分用户纠正的是可读性原则、事实或评估口径，还是本篇排版偏好。可读性原则应用于获授权草稿内具有同类 Reader loss 的其他选项、汇总表、详细章节和术语表，不只搜索相同字面；事实与口径仍以证据为准，本篇偏好不提升为通用写作规则。这是当前编辑的一部分，不另启全仓库审查。

### 7.4 证据不足时的处理

**这是本设计最容易被做错的地方。** 当上述证据都不足以判定 Reader 时，Agent 会倾向于编一个听起来合理的读者画像，然后拿它当前提审查后面的内容——于是整份 findings 建立在虚构标准上。

强制规则：**证据不足时，"这篇文档说不清它的读者是谁"就是它最高价值的 finding，直接报告该缺失，不得推测填补后继续内容级审查。**

这一条同时是本设计对 `#2` 的核心洞察：Purpose confusion 只是症状，说不清读者是根因。

## 8. 审查对象范围

### 8.1 在范围内

面向真人的仓库文档：任何层级的 `README`、`docs/` 下的 Markdown、架构说明、onboarding、runbook、ADR、根目录的设计说明文档。

`optimize-docs-readability` 的写作收尾还覆盖当前任务撰写或大幅修订的面向真人的长文，包括调研报告、文章、方案和多节说明；文件与会话正文均适用，不要求位于仓库。

### 8.2 不在范围内

| 排除项 | 理由 |
| --- | --- |
| Agent-directed file | 读者是模型不是真人，判据不同。`codebase-design` 明确优化的是 AI 可导航性；把真人阅读判据（叙事流畅、渐进铺垫）套上去会损害 agent 表现。仅在显式要求时纳入，且此时 Reader 判定为"维护这份指令的人"。**判定按读者，不按文件名**：文件名清单只是启发，被某个 agent 指令文件以引用方式纳为自身规则的文档同样是 Agent-directed file。本仓库的 `docs/agents/*` 就是这种情况——根 `AGENTS.md` 引用它们作为自己的规则，名字却不匹配任何常见 agent 指令文件名 |
| 由脚本或模板反复生成的产物 | 改动会被下次生成覆盖。发现存在 generator 时，报告"审查对象应为模板/generator"并停下。agent 正在撰写、可以直接维护的长文草稿适用第 9.1 节 |
| 代码内文档 | 注释、docstring、标识符命名不是仓库文档。这是 `streamlit@reviewing-readability` 的范围 |
| 外部约定格式 | LICENSE、法律声明、Changelog 规范格式、第三方模板。见第 9.4 节 |
| Intrinsic difficulty | 主题本身难导致的费力不是缺陷，作者无处可转移这份工作。这是长文档不产出成批误报的主要防线：文档难读与主题难懂必须分开判定，只报前者 |

## 9. 审查与写作协议

### 9.1 触发与输入

Viewer 指定要审的文档，或指定一个 diff base 让 Skill 审"我改过的文档"。

**写作任务自动触发。** agent 完成长文初稿或大幅修订后、最终交付前，必须使用本 Skill 做一遍可读性优化，无需 Viewer 再提出审阅请求。目标就是本轮获授权撰写的草稿，无需用户重报文件名；不要扩展到其他文档。普通短回复不自动触发，Agent-directed file 等排除项仍适用。

写作 agent 根据写作请求和草稿确定 Reader/Purpose，应用第 9.2 节判据，直接修正有依据的可读性问题，并按第 11.1 节核对原意、事实、引用和必要限制。完成后按原任务要求交付修订稿；除非 Viewer 另有要求，不生成独立审阅报告、不加载报告模板。未知事实或缺失需求不能靠润色补齐；无法完成的检查如实说明。只因本次优化改了措辞，不再重复启动新一轮。独立审阅仍按以下范围规则运行，并保持只读。

diff 模式只审查当前仍存在且可读的文档。`optimize-docs-readability` 从差异中排除已删除路径并报告跳过项，不为不存在的文件推定 Reader 或提供改写；过滤后没有可审文档时，报告该结果并结束。

**范围绝不隐式扩展。** 独立审阅没有具名文档也没有 diff base 时，停下询问，不默认全仓库——全仓库是 `audit-docs-landscape` 的低频动作，静默触发会让每次改一篇 README 都付出全仓库扫描的代价。

### 9.2 判据

前置：先完成第 7.2–7.4 节的 Reader/Purpose 判定。

每条判据都是第 7.1 节原理的一个实例，格式统一为**被转移的工作**。列表右列就是这条判据的 Reader loss 模板。

审查者同时检查句子、段落和整篇文档：拆成两句的对照、连续的并列例子、每节重复的收尾都可能产生 Reader loss。词语、标点和格式仅用于定位候选；破折号、三项并列、加粗或某个常用词本身不构成 finding。审查者须结合上下文说明阅读损失，不凭这些特征判断作者是否使用 AI；引文、专名和正在讨论的句式不按其外形判错。

| # | 判据 | Reader 被迫做的工作 |
| --- | --- | --- |
| 1 | **Reader 与 Purpose 缺失** | 自己判断"这篇是不是给我的、读完能得到什么" |
| 2 | **Purpose confusion / 细节层级不当** | 自己过滤掉服务另一类 Reader 或不必要细节层级的内容 |
| 3 | **术语或自造记号未就近解释，或同一所指多个叫法** | 自己去查、猜这个词，或自己确认几个名字是不是一回事 |
| 4 | **重点迟到或被多余表达干扰** | 读完整段才知道这段与他是否相关，或从铺垫、重复和无关对照中筛出实际要点 |
| 5 | **执行主体不可确定** | 自己推断该由谁执行这个动作 |
| 6 | **依赖顺序错误 / 前向引用** | 先把一个未定义的概念记住，等后文引入再回头重读 |
| 7 | **可执行性缺口** | 自己补回缺失的步骤、前置条件、示例的隐含前提，或把量词代掉的清单自己找回来 |
| 8 | **篇内结构与导航问题** | 线性扫描全文才能定位到所需内容，辨别重复段落是否另有含义，或自行重建文字中的关系，包括技术机制与用户可观察结果之间的联系 |

各条的执行细节：

1. **Reader 与 Purpose 缺失。** 根因级 finding，优先于其余各条报告。触发条件见第 7.4 节。
2. **Purpose confusion / 细节层级不当。** 症状：`TUTORIAL` 中途插入完整参数表；`REFERENCE` 里夹叙事解说；一篇文档前半段带着走、后半段变查询手册。**边界**：当两种 Purpose 必须共存时不算缺陷——设计文档必须把理由放在它所支撑的规则旁边，拆开会让两边都变差，这属于 Intrinsic difficulty。此时正确的产出是判据 8 的阅读路径（标明哪些节顺序读、哪些节跳读），而不是建议拆分文档。本文第 13.1 节记录了这条边界被实测触发的过程。

   即使 Reader 和 Purpose 相同，也应按第 7.3 节确定的问题检查细节层级。总览保留职责、关系和必要边界；不帮助回答这些问题的实现细节可省略，或用已核对的现有专项资料链接承接。保留信息意味着主张准确、必要区别清楚，不要求每个视图都重复全部细节。理解或使用主张所需的条件、证据限制和标识符应留在当前上下文，不能用一个链接代替。
3. **术语或自造记号未就近解释，或同一所指多个叫法。** 两个失效模式，都要查。补定义前先判断 Reader 是否需要这个词或记号；可删除无关修饰，或在机制本身无关时使用有来源依据的职责描述。查询源码或区分概念所需的精确标识符应保留，不能为统一叫法而合并不同概念。

   定义存在也可能让 Reader 继续猜。按当前问题需要，解释职责、使用阶段、与相邻概念的关系和适用范围；区分通用概念与某产品专属的格式、实现或名称。展开缩写、笼统称为“生态”不能代替职责说明。不要求每个定义列齐全部信息，不默认新增术语表，也不为补齐定义编造事实。

   **失效模式一：未解释。** 适用对象不只是词，还包括这个仓库自造的记号——编号、缩写、标签、状态码。必须区分三类：**保留下来的项目自造词与自造记号**（内部代号、模块昵称、仓库特有的状态名，以及 `#1`/`#2` 这类自定义编号）——一律必须就近解释，编号还要说明它表示什么、以及排列依据是什么；**行业通用词**（JWT、CI、DAG）——按判定出的 Reader 决定是否需要解释；**与仓库别处定义冲突的词**——该词在本仓库另一处已有定义但含义不同。第三类最隐蔽，因为"就近解释一句"并不足够：必须显式声明与那个定义的关系，否则 Reader 会把两个不兼容的含义混用，而且他越熟悉那份别的文档越容易出错。原合并设计中的 `Viewer` 与 `Reader` 辨析就是实测出来的实例。

   **失效模式二：同一所指多个叫法。** 同一个东西在文中有两个以上名字，Reader 被迫自己确认它们是不是一回事。它与失效模式一不同——词已经解释过了，缺的是一致。正确产出是为该概念在文内固定一个简称并全文统一，而不是在每处补解释。本文曾用"参照来源""来源 Skill""Skill 来源"指同一个参照物，且"前两类的区分来源 Skill 没有"还能被断错句，这是第二轮实测出来的实例。

   三类区分中的前两类沿用参照 Skill；第三类、自造记号与失效模式二都是本文新增。
4. **重点迟到或被多余表达干扰。** 检查开头是否点题：例如 README 前三行没说清“这是什么、给谁用”，或段落迟迟没有交代与 Reader 的关系。审查者判断每句话对 Reader 的作用，包括提供事实、条件、解释、行动信息或导航。仅宣布接下来要讲什么、空泛拔高意义、复述标题或上一段、讲述无关写作过程的句子，在不承担这些作用时建议删除。不能仅凭当前对话已有背景就删掉独立文档所需的解释；读者已知什么仍须由 Reader/Purpose 的证据确定。保留或删除解释句前，说明删掉后 Reader 会失去哪项必要事实、条件、理解或导航；作者展示自己认真核查的过程，不因语气谨慎就有用，影响结论适用范围的证据限制则应保留。审查者还应检查全文中的两类表达，即使句子的结论已经清楚：

   - “不是 A，而是 B”：上下文没有需要澄清的 A 时，直接陈述 B。
   - “是 A，不代表 B／不能说明 B／不能推导出 B”：B 与 Reader 当前问题无关时，直接陈述 A。

   finding 须指出具体的多余对照，以及 Reader 为何被迫判断它与当前问题的关系。审查者删除被否定的内容后，应核对事实、适用条件和 Reader 所需判断是否完整；完整就删除。改写应从原文直接提取要表达的事实，不把多余对照换成另一种否定句式。

   **边界**：对当前问题必需的证据边界、适用限制和误解澄清应保留其含义，优先改为正面说明范围。例如原文支持该范围时，可写“本次测试仅覆盖单机吞吐量”。正面陈述无法保留必要区别时，可以保留对照；审查者必须从原文、上下文或 Reader/Purpose 说明其必要性，不能凭空假设读者会误解，也不能仅因出现否定词就报问题。
5. **执行主体不可确定。** 判据判的是**缺失**（Reader 拿不到执行者），不是某一种句式。四种机制都要查：**被动语态**（"配置会被重新加载"）；**无主句**（"完成后清理临时文件""失败时重试"）；**名词化**（"完成校验后"——把动作变成名词，主体随之消失）；**占位主语**（"系统会重试""流程会清理""相关模块负责校验"——句子有主语、是主动句，但那个主语不是任何真实组件）。

   **中文文档里主要机制是无主句，不是被动句。** 中文技术写作很少用"被"字句，省主语是常态，所以只盯被动语态会在中文语料上系统性欠触发。本文第 13.1 节记录的第二轮 F6（"优先记录不会过期的内容"）就是无主句，不是被动句。占位主语在上下文中没有明确所指时，也会让 Reader 自行推断执行者，符合 Reader-transferred work 的缺陷定义。

   **边界，与扩宽同等重要**：中文里省主语的句子极多，没有边界会成批误报。判定测试是**候选主体是否 ≥ 2 个**——只有 Reader 无法从上下文唯一确定主体时才报。F6 满足（候选是 `audit-docs-landscape` 与 `codebase-documenter`）。反过来，**体裁把受话人固定住的祈使句不报**：`SKILL.md`、runbook 里的命令式，受话人就是执行它的 agent 或值班的人，主体是可确定的。`skills/audit-docs-landscape/SKILL.md` 里与 F6 对应的那句祈使句因此不是缺陷。

   被动语态那一条的理由沿用参照 Skill：被动句**依然准确且依然简洁**，所以在审查时最容易漏过。其余三种机制与这条边界是本文新增。
6. **依赖顺序错误 / 前向引用。** 本条由第 7.1 节原理导出，参照 Skill 没有。判据 4 检查重点表达与多余文字，本条检查全篇的概念依赖顺序。症状：某节依赖后文才定义的术语或状态；"稍后会讲到"之后 Reader 必须挂着一个未闭合的概念继续读。**执行方式是机械比对，不靠注意力**：对每个自造词与自造记号，取它的首次出现位置与定义位置，跨节即为候选，再判断 Reader 在这段距离里是否真的需要这个概念。**任何"补一句定义"的改写建议都必须同时回查该词的首次出现位置**——第 13.1 节记录了这条规则的来历：第一轮把 `Viewer` 的定义补进原合并设计第 6 节，却没回查它首次出现在原合并设计第 2 节，修复本身制造了第二轮的一条 finding。**边界**：真正无法线性化的相互依赖概念属于 Intrinsic difficulty，不是缺陷——此时正确的 finding 是"缺一句前置说明指向定义位置"，而不是"顺序错了"。
7. **可执行性缺口。** 文档独有的失效模式。命令、路径、示例，Reader 照做能不能走通：步骤是否完整、前置条件是否说明、示例是否自洽、被引用的文件与命令是否真的存在。另有两项由第二轮实测补入：**集合型指代必须具名**——"四份根设计文档""两个 orchestrator 设计文档"这类量词加类型名、后面又不紧跟清单的写法，作者知道是哪几份，Reader 得自己列目录找回来；**可数断言必须实测**——文中出现的数量、清单、体积、版本要真去核对，本文第 13.1 节原先写的体积下界就是这样被查出与实际不符的。**边界**：只做存在性、自洽性与可数断言的核对；prose 描述与代码实际行为的语义一致性属于 `neat-freak`，本 Skill 不做。
8. **篇内结构与导航问题。** 标题层级是否反映实际内容组织；长文档是否缺少可跳读的锚点。整理目标文档内的参考资料属于篇内组织，重建仓库级导航仍属于 `audit-docs-landscape`。

   审查者检查各节是否反复使用相同开场、收尾或同义例子，迫使 Reader 比较它们是否增加了信息；检查泛化标签、处处加粗或装饰性标题是否妨碍识别重点与定位内容。改写可以合并重复内容、简化标签或调整标题，但应保留有独立含义的并列项、帮助查找的格式和承担实际阅读作用的重复。

   总览先建立整体，再展开依赖它的局部；读图必需的说明放在图前或图旁，合并需要 Reader 来回寻找的说明。编号、图例位置和强调方式按阅读任务选择，不把某篇文档的布局偏好固化为通用规则。

   同级内容采用一致的分类依据。业务需求、评估口径和实现选择回答不同问题，不能用一个误导性的标题混装。术语表同类条目应集中，除非现有查询顺序能解释其排列；按 Reader 所需的职责或部署阶段等区别分类，不因同一品牌就把转换器和 runtime 归为同类。保留有用的字母序等查询组织，不强制把参考表改成教程顺序。

   对比较内容，审查者先明确每个维度对应的 Reader 问题，并核对：

   - 各选项回答同一问题，粒度相近；独立维度合并后妨碍分别判断时，应拆开呈现，例如模型覆盖与自行训练模型的适配。
   - 先给有证据的结论及必要范围；PR 状态或转换步骤属于证据，不能代替能力是否可用的答案。汇总不需要的核查细节移到证据说明中。
   - 限制以条件及影响表达：什么不能运行、什么能力受限、使用者需要额外做什么。通用依赖只有在排除相关环境或产生有依据的额外义务时，才构成有用的限制说明。
   - 相对优劣须说明比较对象和实质差异。通用维护成本可以与决策有关，但没有负担差异的证据时，不能据此声称某方案相对更差。

   保留文档约定的支持口径及必要版本、模型、设备等范围；证据不足应报告缺口，不能补出排名，也不能把“未核实”改为“不支持”。这里检查既有证据的表达，不独立评判技术方案。

   同时审查已有图表。颜色、边框粗细、分组、位置和箭头可能暗示状态、优先级、包含、拥有或流向，应对照来源和图例检查这些含义。finding 必须指出误导了哪种理解，不能仅凭某种装饰出现就报问题。状态标记应与文字一致；仅重复标题且不能帮助扫读，或妨碍区分时删除，不规定统一的图标集合。

   `optimize-docs-readability` 还应检查密集文字是否让 Reader 自行重建组件关系、流程分支、状态转换、交互顺序或多维比较。**长段落只是检查线索，不直接构成缺陷。** 只有图示能减少推断、记忆或反复翻读时才建议增加；分段、标题或列表足以解决时，使用这些更简单的方式。

   新增图示的形式按信息选择：组件及其关系用架构图或关系图；多分支步骤用流程图，状态转换用状态图；跨角色交互顺序用时序图；多方案、多维度比较用表格。finding 必须指明原文位置、Reader 需要重建的关系与建议形式，在“改写”字段提供可直接使用的 Mermaid 或 Markdown 表格，并说明插入位置或替换范围。图示保留必要的文字说明、条件和例外；装饰性配图或重复已经清楚的解释不构成 finding。

   当已判定的 Reader 需要理解或评审功能行为时（例如，需要判断文章编辑功能如何处理同时编辑的产品经理），`optimize-docs-readability` 检查文档是否把技术机制与具体场景、触发条件、可观察结果和限制联系起来。Reader 必须由第 7.3 节的证据确定，不能统一设为“产品经理”。本项仍归判据 8：Reader 被迫从作者已写下的机制自行推导产品含义，而作者本可以用具体场景解释。只把技术术语换成通俗词语，未必消除了这份推导工作。

   finding 须指出原文已有的信息、Reader 仍需推导的结果，并提供保留原意的场景化改写；文字足以解释时，不强制画图。改写中的条件、结果和限制只能来自原文或其引用说明，不得增加产品承诺、设计理由或补查代码来证明行为。开发者查询 API 的文档不因保留必要技术细节而命中；上下文已有清楚解释时不报。来源没有说明的行为保留为未知，沿用既有缺口与范围规则，不把缺失的产品决策当作措辞问题。

   例如，来源已说明编辑器提交打开时的版本号，文章服务在保存成功后递增版本号，并拒绝版本不匹配的保存。可以建议改写：“两个人打开同一版本的文章后，如果其中一人已经保存，文章服务会拒绝另一人的保存，因为其修改基于旧版本。”来源未说明失败后是否保留输入或如何重试时，不得补写“输入不会丢失”或恢复步骤。类似地，“编译产物管理较多”没有说明部署影响；来源若已明确模型包对应的模型、编译上下文容量和芯片兼容范围，应解释哪些变化需要新包。不能据此推断每款芯片必须单独一包，也不能在来源允许兼容复用时声称一律重新编译。

### 9.3 Finding 格式

每条 finding 四个字段，缺任一字段不成立：

| 字段 | 内容 |
| --- | --- |
| 位置 | `file:line` 或 `file § 标题` |
| Reader loss | 这个 Reader 具体看不懂哪句、卡在哪步、或形成了什么错误预期。不接受"表述不清"这类空转 |
| 判据 | 命中第 9.2 节的哪一条 |
| 改写 | 可直接替换的具体文字，**使用被审查文档自身的语言**——中文文档给中文改写，英文文档给英文改写 |

审查者先确定原段落中有依据的要点，再组织改写建议；逐词替换仍然绕弯时，改写整个相关段落。改写保留项目术语和适合 Reader/Purpose 的作者表达习惯，不为追求自然感补入细节。细节取舍遵循判据 2，句式偏好本身不构成删除事实的理由；第 11.1 节复核信息保留情况及原问题是否消除。

输出顺序：开头一张 Reader/Purpose 判定表（含依据来源），然后按文档分组的 findings，最后一节列出**未产出 finding 的判据及原因**。

最后一节不是可选的。它有两个不可替代的作用：它是第 13.2 节关卡 2 唯一的证据来源——Viewer 据此判断某条判据是执行后通过了，还是被静默跳过了；它也是发现判据本身表述过宽或过窄的唯一途径。本文第 13.1 节记录的两轮结论都来自这一节——第一轮证伪了"判据 2 应在长文档命中"的预测，第二轮暴露了判据 1、2、4 两轮零命中——只看 findings 两次都发现不了。**这一节不得作为冗余删除。**

### 9.4 What NOT to Change

- **许可与法律声明**——措辞有法律后果，不是可读性问题。
- **外部约定格式**——Changelog 规范、issue 模板、徽章语法等由外部工具或社区约定消费的结构。
- **承担阅读作用的重复**——保留帮助导航、总结、教学或安全的重复，包括破坏性操作提示。每句话须有阅读作用，不要求每句都增加新事实。
- **影响判断的依据与限制**——保留研究方法、来源、时间范围、证据限制和真实不确定性；区分这些内容与无关的写作过程叙述。
- **他人署名与致谢**。
- **纯口味型改写**——说不清哪个版本让 Reader 更好过的，不报。

### 9.5 不分优先级

所有 finding 平级列出，不做严重度分级。理由：文档改动便宜，Viewer 逐条看过去的成本低于维护一套分级判据的成本。唯一的过滤器是第 7.1 节的原理本身——说不出被转移的是哪份工作，这条 finding 就不存在。

### 9.6 停止条件

- 审查对象未确定（无具名文档、无 diff base、无当前写作草稿）→ 停下询问，不猜。
- 对象会被脚本或模板重新生成覆盖 → 报告应改 generator，停下。
- 对象是 Agent-directed file 且 Viewer 未显式要求 → 报告已跳过及理由。
- 第 7.4 节触发（读者判定无证据）→ 报告该缺失，不进入内容级审查。

Skill 的八条判据由 `SKILL.md` 承载，报告模板单独存放；当前没有 `scripts/`、`tests/`、`evals/`。执行 Skill 的 agent 仅在第 4 步起草独立审阅报告时加载本 Skill 的模板，取证阶段不加载；第 5 步复用模板记录证据复核结果，再保存和交付报告。写作收尾不加载报告模板。判据需要成篇的正反例时，再增加对应的参考文件。

## 11. 输出与落盘

独立审阅时，本 Skill 默认将完整报告保存到被审仓库根目录下的 `.scratch/docs-review/`；非 Git 项目使用工作区根目录。执行 Skill 的 agent 根据审查目标确定根目录，不使用 Skill 安装目录或特定电脑的固定路径；输出目录不存在时创建。写作收尾按第 9.1 节交付修订稿。

报告命名如下，`<date>` 使用 `YYYY-MM-DD`：

| Skill | 文件名 | 目标取值 |
| --- | --- | --- |
| `optimize-docs-readability` | `<date>-readability-<target>.md` | 显式 diff 模式固定用 `diff`；多个具名文档用 `multi-docs`；单篇用去掉扩展名的文件名。完整选中文件列表与 diff 基准记在报告内 |

agent 将名称中的空白和文件名非法字符（`/ \ : * ? " < > |`）替换为连字符。同名文件已存在时，agent 在 `.md` 前依次追加 `-2`、`-3` 等后缀，不覆盖已有报告。会话内返回简短摘要和报告链接。Viewer 显式指定路径或要求不落盘时按其要求执行；保存失败时，agent 在会话内交付完整报告并说明未保存及原因。

**独立审阅不写入被审查文档。** 写作收尾仅修改本轮已经获授权撰写或修订的草稿。

### 11.1 保存与交付前的证据复核

独立审阅的 agent 在第 4 步完成报告草稿后，于第 5 步进行一次基于原文件的证据复核；写作收尾的 agent 对照优化前的草稿和已有来源执行同样的内容检查。不默认增加第二个 reviewer；即使没有 findings，也必须复核检查覆盖情况。

| agent 必须核对的内容 |
| --- |
| 逐条确认原文位置、Reader 判定依据，以及上下文或引用说明是否已解决所报问题；对照原文检查改写保留原意、条件与执行主体职责，没有引入未经证实的信息；补定义时回查首次出现；对建议的图示或表格逐项核对节点、连线、条件、顺序和比较项都有原文依据，删除虚构关系或误导性简化；逐篇核对八条判据的发现、无发现与停止状态 |

`optimize-docs-readability` 的 agent 逐项对照改写前后的事实、名称、数字、日期、引用、排序、时序、适用条件和确定程度，检查增添与遗漏。不得把“可能”改成“确定”、“相关”改成“导致”，或把“尚未核实”写成“确认不存在”；信息取舍遵循判据 2，删减后应核对保留主张的适用范围、证据强度和必要限制。agent 再把改写放回段落和全文语境，检查原 Reader loss 是否仍以其他措辞存在，尤其是多余对照、重复收尾、同义并列和空泛标签。这些检查属于本次证据复核，不另设审查轮次。

agent 还须对照获授权草稿中重复出现的主张，确认汇总表、详细章节、术语表和示例的名称、支持状态、范围与条件一致，并检查用户反馈影响的其他同类选项。保留各处合理的细节差异，不复制整段说明到所有位置；独立审阅只报告不一致。

图示相关 finding 应查看实际画面，用户提供的截图可以作为审阅依据。修改布局、连线或强调方式后，应重新渲染目标格式下受影响的视图，检查箭头连接点与方向、文字截断或重叠、分组和可辨识性。Markdown 格式问题应在目标预览器核对受影响的标题、表格、加粗、行内代码和状态标记。例如 `**标签：**正文` 可能无法按预期渲染，移出标点是一种修法，但仍需预览确认。语法通过不等于视觉通过；无法查看渲染结果时列为未验证，普通措辞修改不触发无关图示复查。

任务明确了 HTML、Markdown 等多个维护版本时，检查范围内各版本本次修改的标题、顺序、术语、引用和图示含义是否一致。写作模式同步获授权的版本，独立审阅报告差异；保留适合各格式的布局，不要求像素一致，也不自行发现和修改无关副本。

agent 删除误报、修正证据不足的结论或改写，并对修正后的 finding 核对证据。无法核实的结论移入未验证项，不作为已确认 finding。独立审阅用报告模板记录复核方式、核对的证据、修正摘要（或无修正）及未验证项；写作收尾按第 9.1 节交付正文并说明未完成的检查。此环节是同一 agent 的证据自查，不冒充独立复核，也不保证没有遗漏。

## 12. 关键取舍

### 12.1 Skill 与设计文档各自分开

Viewer 在 2026-09-03 选择拆分。逐篇审查是高频、范围小、可以只对改动过的文档跑；全仓库盘点是低频、范围大。合成一个会导致每次改一篇 README 都触发全仓库扫描。原设计为保持共同基础一致，合并为一份设计文档。2026-10-02 按 Viewer 要求调整为一个 Skill 对应一份 design；维护者修改共同原则或职责边界时，需核对另一份设计，避免两边冲突。

### 12.2 未证明需要前不写脚本

本 Skill 的内容判据由 `SKILL.md` 承载，当前不引入脚本和测试。原合并设计中唯一确定性可计算的链接图遍历属于 `audit-docs-landscape`；它的首版取舍与脚本提取条件见 [`audit-docs-landscape` 设计](./audit-docs-landscape-design.md) 第 12.2 节。本 Skill 需要成篇的正反例时再增加参考文件，评测触发条件见第 13.3 节。

### 12.3 自动推定读者而不是每篇都问

Viewer 在 2026-09-03 选择自动推定。逐篇确认读者会把一次审查变成一轮问答，抵消掉 Skill 的价值。代价是推定可能出错，因此第 7.3 节要求列出推定依据、第 7.4 节禁止无证据推测——把出错变成可见且可纠正的，而不是隐藏在 findings 背后。

### 12.4 独立审阅与写作收尾

独立审阅提供 findings 和具体改写建议，Viewer 决定哪些落地。写作任务已授权 agent 完成稿件，可读性优化在交付前完成；第 9.1 节限定为当前草稿，不把审阅请求解释成修改原文的授权。

### 12.5 排除 Agent-directed file

Viewer 的原始诉求是"对真人可读"。`AGENTS.md`、`SKILL.md` 这类文件的读者是模型，判据不同甚至相反。若纳入，Skill 会用真人阅读标准"优化"这些文件的措辞，直接损害 agent 表现。代价是这些文件的人类维护者拿不到审查——需要时显式要求，且此时 Reader 判定为维护者。

### 12.6 `optimize-docs-readability` 不分级、`audit-docs-landscape` 分级

不对称是有意的，依据是修复成本：改一句话便宜，写一篇文档昂贵。分级只在修复成本高到需要排序时才值得维护。

### 12.7 用一条统一原理，而不是保留经验清单

草案的判据是三个来源拼起来的：Diátaxis 覆盖一条，`streamlit@reviewing-readability` 借来三条，其余四条自创无来源。清单本身可能是对的，但它有两个具体代价：无法拒绝将来提出的第九条判据，也无法在某条判据产出误报时判断是判据错还是执行错——只能靠试错删除。

改成从第 7.1 节原理派生后，判据有了准入测试和排除规则，并立即导出了清单遗漏的判据 6（依赖顺序）。代价是原理本身可能被滥用成"Reader 需要思考就是缺陷"，因此第 7.1 节末尾和第 8.2 节的 Intrinsic difficulty 排除必须同时保留，缺一条就会产出成批误报。

保留经验清单的替代方案不是错的，但那样第 13.2 节的"只产生误报就删除"就是唯一的质量机制，等于用试错替代原理。

## 13. Verification strategy

Viewer 在 2026-09-03 选择先不做评测，直接使用。因此本节定义的是**首轮人工验证**和**引入评测的触发条件**。

### 13.1 首轮验证语料就用本仓库自己的文档

本仓库是理想的首轮试验对象，且每类都有真实样本。**语料顺序按"哪条判据还没被证过"排，不按文档类型排**：两轮自审之后判据 1、2、4 仍是零命中，所以下一轮先跑能打到这三条的语料，而不是继续跑长设计文档。

| 对象 | 验证什么 |
| --- | --- |
| `CONTEXT.md`（**下一轮先跑**） | `REFERENCE` 型文档，判据 2 不应把词汇表的跳读结构误报为混乱。判据 2 两轮零命中都是被 Intrinsic difficulty 排除正常拦下的，这里是它唯一能正面命中的本仓库语料 |
| 外部仓库的 README 或 `TUTORIAL` 型文档 | 判据 1、4 的唯一验证途径。本仓库无顶层 README，全部文档都是 `EXPLANATION` 或 `REFERENCE`，所以这两条的零命中无法区分"判据表述太窄"和"语料打不到"——在拿到这类语料之前不得据此删改判据 1、4 |
| 2026-09-03 的四份设计语料：拆分前的合并设计、`write-implementation-tickets-design.md`、`execute-tickets-design.md`，以及后续随监控需求删除的 spec-monitor-design.md（当时记录为 35KB–120KB） | 长文档。**原合并设计已执行**，产出 6 条 finding，命中判据 3、5、6、7、8。判据 6（依赖顺序）独立产出了一条 finding，不是靠别的判据顺带发现的，说明这条新判据成立。**原先"判据 2 应在长文档命中"的预测被证伪**：设计文档混用 `EXPLANATION` 与 `REFERENCE` 属于 Intrinsic difficulty，排除规则先把它拦下了，正确产出是判据 8 的阅读路径。该边界已写入第 9.2 节判据 2。**第二轮已执行**（同日，修完第一轮之后再跑）：产出 7 条 finding，命中判据仍是 3、5、6、7、8，判据 1、2、4 两轮零命中。第二轮抓到的是指代不具名、记号未解释、同一所指多个叫法这类精度缺陷，与第一轮的缺定义、缺阅读路径不在同一层次，说明同一份文档多轮运行不会只是重复。**第一轮的修复本身制造了第二轮的一条 finding**：把 `Viewer` 的定义补进原合并设计第 6 节时，没有回查它首次出现在原合并设计第 2 节 |
| 某个状态推导/投影一类内在复杂的技术小节 | 专测 Intrinsic difficulty 排除。状态推导本身有内在复杂度，正确结果是只报"缺一句指向定义位置的前置说明"，不报"这节太复杂" |
| ADR（`EXPLANATION` 型，读者与目的明确，findings 应当很少；出现大量 finding 是误报信号） | **当时本仓库没有 ADR**——原 `docs/adr/` 四篇都是监控需求的，已随 spec-monitor 一并删除。这条语料要等本仓库产生新的 ADR，或改用外部仓库的 `docs/adr/` |
| `docs/agents/*` | 边界样本，**已执行**。结果：暴露出排除规则原本按文件名匹配的缺陷——根 `AGENTS.md` 引用这些文件作为自身规则，读者是模型，但名字不匹配任何常见 agent 指令文件名。修正已写入第 8.2 节 |

### 13.2 判据是否成立的判定标准

两道关卡，顺序固定：

1. **派生测试**（写 `SKILL.md` 时就执行）：这条判据能否写成"Reader 被迫做 X，而作者本可以做掉 X"。写不出来的不进 `SKILL.md`，不必等首轮验证。
2. **经验测试**（首轮验证后）：它至少产出一条 Viewer 认可的 finding，且没有产出成批误报。只产生误报的判据删除，不是调参保留。

一条判据过了关卡 1 但在关卡 2 失败时，先检查是执行偏离了原理还是判据本身表述过宽，再决定改措辞还是删除——不要直接删，那会丢掉原理已经证明成立的东西。

### 13.3 引入评测的触发条件

出现以下任一情况时，按 `skill-creator` 的评测流程补 eval：

- 同一条判据在不同仓库上表现相反，无法靠读 `SKILL.md` 判断哪次是对的；
- 修改判据措辞后无法确认是改好了还是改坏了；
- 第 7.4 节的无证据禁令被违反，即 findings 建立在虚构读者画像上；
- 第 8.2 节的 Intrinsic difficulty 排除失效，即主题本身难被报成可读性缺陷。

最后两条是最需要评测保护的行为：它们都不会让输出看起来有问题，只会让输出安静地建立在错误前提上。

## 14. 修改本设计时必须保持的不变量

### 14.1 约束修改本设计的人

1. 缺陷的定义是第 7.1 节的 Reader-transferred work：作者把本该自己做的工作转移给了 Reader。判据不得脱离这条原理独立存在。
2. 每条判据必须能通过派生测试——写成"Reader 被迫做 X，而作者本可以做掉 X"。通不过的不进 `SKILL.md`。
3. 未证明需要前不引入脚本；判据全部由 `SKILL.md` 承载。本 Skill 的脚本取舍见第 12.2 节。
4. 判据 3 必须保持两个失效模式（未解释、同一所指多个叫法）与三类区分（项目自造词与自造记号、行业通用词、与仓库别处定义冲突的词）。少任何一项，它会产出噪音、漏掉最隐蔽的一类，或漏掉"词解释过了但叫法不统一"这整个失效模式。

### 14.2 约束 Skill 的运行时行为

1. Intrinsic difficulty 不是缺陷。主题本身难导致的费力不报，作者无处可转移这份工作。
2. 内容问题按信息是否存在分工：已写下但文内表达让 Reader 自己找回来 → `optimize-docs-readability`；从未写在任何地方 → `audit-docs-landscape`。跨篇导航始终属于 `audit-docs-landscape`，包括已有文档从入口不可达的情况。
3. Reader 与 Purpose 判定先于一切内容判断；任何内容级 finding 必须能追溯到"这篇给谁看、要他达成什么"。
4. Reader 判定必须有第 7.3 节的证据。证据不足时该缺失本身是最高价值 finding，不得推测填补后继续审查。
5. 独立审阅为 review-only：仅允许按第 11 节创建审查报告及输出目录。`optimize-docs-readability` 的写作收尾仅可修改本轮获授权撰写或修订的草稿。
6. 每条 finding 必须说明具体的 Reader loss。说不出的丢弃。
7. `optimize-docs-readability` 的范围来自具名文档、显式 diff base，或写作任务中的当前草稿，绝不隐式扩展到全仓库。
8. `optimize-docs-readability` 只做存在性与自洽性检查；prose 与代码行为的语义一致性属于 `neat-freak`。
9. Agent-directed file 默认不在范围内；显式纳入时 Reader 判定为维护者，不套用真人阅读判据。
10. 会被脚本或模板重新覆盖的生成产物不作为审查对象，generator 或模板才是；agent 正在撰写的可维护草稿可按第 9.1 节优化。
11. `optimize-docs-readability` 不分优先级，`audit-docs-landscape` 按被卡住的代价排序。这个不对称由修复成本决定，不得统一。
12. 改写建议使用被审查文档自身的语言。
13. 两个 Skill 都不负责从零撰文、不逆向规格、不做文档与代码的漂移对账；`optimize-docs-readability` 可优化写作任务中已有的当前草稿。
14. 独立审阅必须报告未产出结果的判据及原因，见第 9.3 节。写作收尾执行同样的判据与复核，按第 9.1 节交付正文。
15. 两种 Purpose 必须共存时，产出判据 8 的阅读路径，不产出拆分文档的建议。
16. 任何"补一句定义"的改写建议必须同时回查该术语或记号的首次出现位置。这条来自实测：第一轮的修复正是因为漏了这一步而制造了第二轮的一条 finding。
17. 判据 7 包含集合型指代具名与可数断言实测；这两项属于自洽性检查，不因为"像是 `neat-freak` 的活"而省略。
18. 判据 5 判的是执行主体缺失，不是某一种句式。四种机制（被动语态、无主句、名词化、占位主语）与"候选主体 ≥ 2 个才报"这条边界必须同时保留：只留机制会在中文文档上成批误报，只留边界会退回只抓被动句。
