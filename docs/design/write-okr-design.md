# write-okr 设计

本 Skill 面向需要把工作方向或已有草稿写成 OKR 的用户，支持初稿、精简、局部修改和定稿审阅。本文供维护者理解其方法依据、写作约定与验证方式；执行协议见 [SKILL.md](../../skills/write-okr/SKILL.md)。

## 方法依据

Skill 采用 [Google’s OKR Playbook](https://www.whatmatters.com/resources/google-okr-playbook) 中的目标价值、可验证结果和整体充分性原则：全部 KR 完成后，应足以支撑 O 达成。对收益尚未确定的研究和实验，参考 What Matters 的 [Learning OKRs](https://www.whatmatters.com/faqs/learning-okr)，将待验证问题和有依据的决策作为结果。

不同方法对目标分类、条目数量和评分方式有不同实践。Skill 保留承诺型与挑战型的区别，并允许有价值的工程产出和里程碑；不把某一种分类、固定条数或“完成 70%”当成通用标准。完整来源与适用边界保留在 `SKILL.md` 中，维护时不把写作偏好升级为理论要求。

## 已确认的契约

- 执行者先复用对话、用户最新草稿和提供的材料，只澄清会影响目标、范围或承诺的缺失信息。已确认的选择与用户删除的内容都属于修改约束。
- 执行者按独立结果组织 KR。同一工作的验证、比较与决策可以合并；条目数量以足以证明 O 达成为准，精简时保留必要结果。
- 交付和改善目标写清验收条件；探索任务写清验证对象、比较维度与结论。有充分证据的“不采用”可以完成探索目标，未完成验证不能算完成。
- 数字区分实测基线、理论估算、目标值和采用门槛。采用门槛决定是否继续接入，不等于必须找到达标方案；缺少依据时不编造必达百分比。
- 默认交付简洁的 O + KR，按需另列共用验收口径。正文长度、排期位置和条目数量可按用户要求调整；不把单个项目的技术路线和指标固化为默认值。
- 局部修改只调整指定内容及直接影响的口径，保留已确认目标和术语。定稿审阅只处理影响理解或验收的实际问题，无实质问题即可结束。

## 依赖与边界

运行时入口是 `SKILL.md`；`agents/openai.yaml` 提供显示名称和调用示例。普通写作不依赖其他 Skill、脚本或独立子 agent。用户提供本地文件或要求核实外部事实时，执行者使用当前环境相应的读取、联网能力。

本仓库的 `write-okr/` 是维护源，宿主搜索路径中的副本用于运行，按仓库维护约定手动同步。设计文档留在本仓库，不是安装包的运行依赖。

交付通常直接写在对话中；用户要求文件时按指定位置保存。撰写 OKR 不授权执行其中的合并、发布、采购、消息发送或定时跟踪，也不自动扩展为技术调研或实施计划。

## 必要验证

- 使用 skill-creator 的 `scripts/quick_validate.py` 检查包格式；核对 `agents/openai.yaml` 的调用名与 `SKILL.md` 一致。
- 用代表性请求检查写作行为，重点覆盖下列情况。验证范围随实际修改选择，不为单纯导航或措辞调整重跑全部场景。

| 场景 | 验收要点 |
| --- | --- |
| 已有量化目标，但探索收益只有理论估算 | 保留已确认目标；将探索写为实测比较和采用结论，不承诺未经验证的资源收益或质量无损 |
| 用户只要求修改一条 KR 的术语 | 只改指定条目，不重写其他目标，也不恢复被删除的内容 |
| 用户要求保留截止日期，以实验里程碑支持选型 | 保留日期与必要里程碑，将接入门槛和完成验证分开，不要求一定选出胜者 |

创建时已完成包格式检查和上述三类请求推演。这是有限场景下的行为检查，不代表已证明能够减少所有任务的沟通轮次；后续维护按新增问题补充验证。
