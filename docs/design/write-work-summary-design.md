# write-work-summary 设计

本 Skill 帮助用户把季度或阶段工作整理为有证据支撑的主题成果，并与已有 OKR 对应。本文供维护者理解写作取舍、适用边界与验证方式；执行协议见 [SKILL.md](../../skills/write-work-summary/SKILL.md)。

## 方法依据

规则来自一次季度工作总结的多轮打磨：用户需要让不熟悉具体工作、但懂一些技术的负责人和 HRG，看懂负责范围、关键成果及其对项目的作用。主要困难是把技术记录转成成果叙述，同时保留指标条件、完成程度与贡献归属。

这些规则是实践中形成的写作约定。具体项目、设备、章节数量和句式仅用于说明判断方法，不作为其他总结的默认事实。典型改写与取舍见[打磨案例与取舍](../../skills/write-work-summary/references/editorial-examples.md)。后续维护应提炼用户修改背后的原因，避免把一次删日期、合并章节或调整括号的选择变成通用要求。

## 已确认的契约

### 按主题呈现成果，就近关联 OKR

默认先给总体结论，再按宏观工作主题展开成果，标题就近标注对应 O/KR。架构、能力建设和缺陷修复通常是同一主题内的贡献方式，直接作为主题会让读者自行拼接项目结果。

用户提供完整 OKR 时，默认在成果正文后附原文，供读者查阅原定目标。用户已有模板优先，允许将 OKR 放在开头。执行者保留历史目标的措辞、顺序和承诺，核对正文编号，不把目标改写成已完成事实；缺少 OKR 原文时不编造编号。

一组成果可以对应多个 KR。交付接入与集成问题是否分节，取决于是否形成独立、值得展开的结果。局部修复缺少独立展示价值时，可以合并到项目接入成果，不为覆盖每条 KR 单独凑一节。

### 用实际结果约束表述

- 原型、可运行版本、局部验证、项目集成与客户交付分别表示不同完成程度。执行者依据材料写结果，不能从 KR 的「零阻塞、无延期」目标推导已经达成。
- 技术问题优先说明对使用的影响。例如模型无法加载、图文回答错误和 OCR 漏识别应分别说明，不能统一改写成「精度下降」。
- 关键改善已有可靠解释、且有助于读者判断贡献时，执行者用一句话说明关键做法如何影响结果。实测改善与机制解释分别表述，不能凭机制解释推算单项收益，也不要求每项成果都解释原理。
- 原有能力与新增能力必须区分。「支持」可以描述接入后的能力范围；「新增」「补齐」需要材料证明本期发生了对应变化。
- 同类修复按共同作用合并，保留影响结果判断的边界。次要事项可以留在详细记录中，总结不承担完整提交清单的职责。
- 工程实践写清可复用产物、实际使用对象和用途。用途不同的部署 SOP 应分别解释，不能仅因都提供模型服务就合成一个笼统成果。

### 分层保留数字和证据

有可靠量化结果时，摘要展示关键数值，正文保留比较关系与必要条件，详细统计由已有报告承接。指标保留专业术语、单位、统计量和比较范围；推荐方案或配置只适用于证据覆盖的范围。没有量化数据时，以已形成的能力、交付物和实际应用说明成果，不补造指标或设置空白性能表。

执行者区分个人、团队和外部贡献。整体版本收益可以作为集成与适配成果，归因到单项工作须有对照或其他归因证据。准备写入云文档的总结就近保留可分享链接，内部仓库路径和证据索引留在已有内部记录中。

### 以用户最新稿为修改依据

执行者修改前读取最新目标，保留用户手工润色、已确认术语和删除决定。局部修改仅覆盖目标及直接关联位置；用户只问含义或要求审阅时，先解释并给出建议。

用户要求完整稿时，展示与保存文件一致的全文。普通整理复用现有材料，具体事实不清时再读取直接相关证据，避免扩展为全仓审计或重新运行实验。

## 依赖与边界

安装包保留三个文件，各自承担不同职责：

| 文件 | 作用 |
| --- | --- |
| `SKILL.md` | 任务识别、成果组织、证据边界与迭代规则 |
| `references/editorial-examples.md` | 按需读取的改写案例，帮助判断细节取舍 |
| `agents/openai.yaml` | 显示名称、简要说明与调用示例 |

本仓库的 `skills/write-work-summary/` 是维护源，宿主搜索路径中的副本用于运行，按仓库约定手动同步。设计文档留在 `docs/design/`，不是安装包的运行依赖。

普通写作不依赖脚本、独立子 agent 或固定项目仓库。长文收尾使用可用的 `optimize-docs-readability` 与 `tech-doc-style-chinese`；未安装时执行者自行检查，不阻塞写作。

制定下一周期 OKR 使用 [write-okr](../../skills/write-okr/SKILL.md)。工作总结任务不授权执行报告中的工程任务、上传或发布云文档，也不默认追加验收状态、待办或实施计划。影响成果解读的未完成状态和证据限制仍须保留。

## 必要验证

- 使用 skill-creator 的 `scripts/quick_validate.py` 检查包格式，核对 `agents/openai.yaml` 的调用名与目录名一致。
- 检查包内相对链接、设计文档与仓库导航入口，确保安装包不依赖本机绝对路径或仓库外的临时材料。
- 修改写作规则时，按变更选择代表性请求验证行为，不以固定措辞或标题匹配代替判断。

| 场景 | 验收要点 |
| --- | --- |
| 零散记录混有架构、接入和修复事项 | 按项目或产品主题组织，关联实际服务的 O/KR，避免重复认领 |
| KR 要求商业化交付，材料只有原型或接入记录 | 保留目标原文，成果只描述材料能够支持的完成程度 |
| 材料同时有绝对速度、提升比例和测试报告 | 摘要突出当前水平，正文保留关键比较、条件和链接，不夸大优化归属 |
| 材料同时包含已实现能力、实测收益和待验证方案 | 只将已完成且有证据的内容写入成果；机制解释不冒充独立收益，候选方案不写成已完成工作 |
| 用户已有模板，或手工删改了局部内容 | 遵从最新结构和术语，不恢复旧稿；只改授权范围 |
| 同类部署服务用于不同目的 | 写明各自产物、使用对象与实际作用，不合并为无法判断的笼统收益 |

首次纳入仓库时保留了安装副本的运行规则与案例，仅补充设计文档和导航。当时的验证范围为文件一致性、包格式与本地链接，未新增独立写作场景评测。
