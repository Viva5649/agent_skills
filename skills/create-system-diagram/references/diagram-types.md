# 图类型规则

先按每张主视图要回答的问题选择图类型，再读取对应章节。三类图共用[视觉语法](visual-grammar.md)，按内容叠加[专项规则](specialized-rules.md)。同一 HTML 可以包含多类视图；混合视图须标明节点和关系类型，并确定主要问题。

| 图类型 | 适用问题 | 节点与连线 | 阅读验收 |
| --- | --- | --- | --- |
| 架构图 | 哪些模块承担什么职责，如何组成与协作 | 节点表达架构单元；连线表达依赖、调用、实现或协作 | 找到职责承担者、包含依据与协作对象 |
| 流程图 | 输入或事件如何推进到结果 | 节点表达功能操作、判断或结果；连线表达顺序、条件与循环 | 从入口追到结果，解释实际出现的分支与循环 |
| 数据流图 | 数据在哪里产生、传递、保留和使用 | 节点表达数据、存储及必要处理操作；连线表达读写、传递、复制或映射 | 从来源追到使用端，解释保留与变化 |

## 架构图

适用范围：模块分层、组成、职责协作与运行实例关系。按有依据的架构单元确定粒度，保留同层可比较的身份与边界；组件卡片可以说明多项职责。执行步骤只在需要解释局部协作时展开，并标明步骤含义。

### 按架构职责划分模块

按架构职责划分模块，源码归属作为核对依据。根据模块对外承担的责任、内部协作、资源与生命周期归属确定边界。大框表达大模块的职责边界，小框展开内部组成与分工，连线表达模块间的调用、依赖或数据交接。

分组标题优先说明职责，目录、包名和构建模块名作为次级标识或来源链接。结合接口、生产调用和配置核对分组；同一代码包可以承载多个架构职责，一个架构模块也可以跨代码包实现。实现分布与职责边界有差异时，标明映射，保留真实的协作与资源归属。

支持组件按服务对象和管理责任归组，共享能力按实际复用与依赖关系组织。不能为了把同色组件放在一起而改变包含关系。进程和部署边界单独标明；源码结构、包依赖或构建集成视图可以按源码与构建关系组织，并在标题或图注中明确视图用途。

### 模块、子模块与职责分区

绘图代理先确定图要回答的问题和展开范围。用前三项确认模块身份，展开子模块时再核对包含依据：

| 判定项 | 需要核对的内容 |
| --- | --- |
| 架构身份 | 代码或已确认设计将对象作为稳定的协作单元，有明确名称与实际对应对象 |
| 职责边界 | 能说明模块承担哪些能力，以及哪些工作由其他模块负责 |
| 协作边界 | 能说明其他对象如何调用、依赖模块或与模块交换数据，关系可明确连接到模块 |
| 包含依据 | 子模块承担父模块整体责任中的明确部分；仅有使用关系时，通过依赖线表达 |

现状图依据生产实现或已确认的外部现状，方案图依据已确认设计。涉及状态或资源时，继续核对创建、持有、修改和关闭责任。名称、功能相近或源码目录只提供线索；证据不足的结构保留待确认，不凭排版补出模块。

外层与内层表示模块之间的包含关系。当前视图可以只展示单模块，也可以展开有依据的子模块。职责表示模块承担的工作，执行主体仍是所属模块。父模块可包含子模块，各模块可同时展示职责；整体职责涉及多个子模块时，注明适用范围与责任方。模型、文件、产物等保留实际类型，不因使用卡片就改称子模块。

优先展示回答本图问题所需的子模块，再补充必要职责。职责可以写在模块卡片内，也可以用列表、短条或分区；短条可有细边框，通过标题、尺寸和排版与模块卡片区分。请求和结果关系连接实际模块或组件；职责分区只有在明确展示局部步骤时才承担相应流程关系。

## 流程图

适用范围：需要解释任务如何完成的图，包括架构图中的局部流程。先确定一次请求、一个批次、某一轮或完整任务的范围，以及入口事件、完成结果和必要前提。调用返回、业务完成与资源清理分别核对，只有影响本图问题时才展开对应边界。

### 功能操作的拆分

每个操作块应能回答：执行者在什么输入或状态下，完成什么操作，得到什么结果。根据读者需要区分的结果、依赖、状态变化或开销拆分，保留同层粒度。

| 视角 | 拆分依据 | 放入明细的内容 |
| --- | --- | --- |
| 业务 | 有独立完成条件的任务进展 | 不影响任务理解的内部步骤 |
| 工程 | 组件责任交接、等待、存储或需要分析的成本边界 | 单纯函数拆分、变量赋值与封装层 |
| 算法 | 回答当前问题所需的数据变换、关键状态读写与依赖 | 同一操作内的公式推导与实现细节 |

例如「计算统计结果」与「写入结果文件」在分析计算与写入开销时分别成块；一般任务总览可以合为「生成报告」。函数或公式数量本身不决定块数。组件节点与操作节点混用时，就近注明操作的执行者。

复杂链路或粒度尚有争议时，先选包含关键依赖的一小段画出示例，再按同一标准展开全图。材料足以确定的粒度由代理选择；仍会改变用户要求的展开范围时，先澄清。概念解释不会自动扩大已确认的图稿范围。

### 顺序、分支与循环

- 主线覆盖从入口到结果所需的功能操作；工程或算法完整链路是阅读目标时，不能全部隐藏在业务节点的展开内容中。
- 分叉说明择一、并行或广播，条件紧邻分叉。授权、另行发起等前提在实际入口可见；文件交接与执行触发分别表达。
- 出现循环时，明确重复范围、迭代推进和退出条件。例如「批次 i +1，继续处理下一批」；已有迭代变量时沿用原名。首轮与后续轮次不同则标明差异，跨轮读写的状态按资源与存储专项核对。
- 条件退出接在实际触发位置，取消或错误出口不排成每次必经的普通阶段。初始化、每次请求与满足条件时才发生的操作分别注明触发时机。
- 箭头、编号与完成条件核对当前实现或指定设计。通用教材流程只能辅助理解，不能覆盖实际调用顺序；编号表示索引还是执行顺序须明确。

验收时追踪一条完整路径；图中有分支或循环时，再追踪一个能解释条件与退出的实例。没有这些内容的图无需补出分支或循环。

## 数据流图

适用范围：需要解释数据来源、去向、转换、存储或复用的图。先确定展示的是逻辑数据、存储对象还是物理分配；按本图问题选择节点身份，需要混合时明确类型与对应关系。

- 为主要数据标明来源、接收者及必要的读写者。处理操作写明输入和输出；同一数据跨阶段保留时，保持可识别的身份。
- 连线区分读取、写入、同一存储区域内复制、跨区域复制、映射与别名。复制方向跟随数据去向，依赖箭头另行声明；多个视图指向同一分配时标明共享关系。
- 新建节点须有独立数据或存储身份依据。操作数量不决定分配数量，视图与别名通过明确关系关联实际分配。
- 读写与跨阶段保留是主要问题时，可将存储区域或 buffer 固定为列，执行进展向下，读写横向展开。持久状态保留在同列，后续读取接到实际保留状态；相关生命周期见专项规则。
- 固定列只适用于需要持续追踪存储的内容。一般数据转换可以使用直接的来源、处理与目标布局，无需增加介质列。多阶段重复展示同一对象时，注明同一对象及阶段。

验收时从输入追到最终使用端；存在跨阶段状态时，继续追踪其写入、保留和后续读取。仅凭图内信息应能区分数据变换与数据搬运。
