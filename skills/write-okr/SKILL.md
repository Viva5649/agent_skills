# 撰写与精简 OKR

把用户的工作方向变成少量独立、可验收的结果。默认直接交付 O + KR；已有草稿时尊重用户最新版本，不重新开展一轮规划。

## 方法依据与适用边界

以 Google 的公开实践和 John Doerr 团队的 What Matters 方法为依据，采用其中一致的核心原则；不宣称存在统一的行业硬标准。

- **价值与聚焦**：O 表达值得投入的变化，能说明对用户、业务或能力的价值；有挑战性，不是把所有日常工作换个标题。
- **可验证**：KR 用明确标准和可检查证据判断进展，不能仅靠“已投入努力”。
- **整体充分**：逐条相关还不够；全部 KR 完成后，应足以支撑 O 达成。精简不能漏掉实现目标所必需的结果。
- **周期与跟踪**：OKR 有明确周期、责任人和复盘依据。周期可统一写在上下文中，不必重复进每条 KR。以上原则主要依据 [Google’s OKR Playbook](https://www.whatmatters.com/resources/google-okr-playbook)。
- **承诺与挑战分开**：承诺型要求兑现；挑战型允许存在未达成风险，但标准仍须清楚。Google 的挑战目标平均 0.7 分是其评分实践，不能套成所有目标“完成 70% 就算成功”。参见 [Committed vs. Aspirational OKRs](https://www.whatmatters.com/faqs/committed-aspirational-okrs-examples-difference)。
- **不确定性可以成为学习目标**：What Matters 提出 Learning OKR，用来验证假设、减少未知。本 skill 将其用于探索任务；这是有来源的方法扩展，不是所有流派统一采用的第三分类。参见 [Learning OKRs](https://www.whatmatters.com/faqs/learning-okr)。
- **优先衡量影响，允许有价值的产出**：What Matters 也允许 input、output、outcome KR 的组合。工程性能指标、验证结论、必要里程碑可以入选，但必须说明如何支持 O，不能机械禁止所有交付型 KR。参见 [Inputs, Outputs & Outcomes](https://www.whatmatters.com/okrs-explained/input-output-outcome-key-results)。

以下“条目少、正文短、排期单列、只改指定部分”是本 skill 的写作默认，不是 OKR 理论定律。用户的格式、组织规则和已确认选择优先；不固定目标数量、百分比、人力或季度长度。写普通 OKR 时不必向用户复述理论，也不必为这些稳定原则重新联网。

## 1. 先复用上下文

- 从对话和材料提取目标、范围、负责人或人力、周期、已确认指标和表达偏好。用户删除或否定过的内容也属于约束，不要恢复。
- 只问会实质改变目标、范围或承诺的问题；已有答案不再问。不影响起草的信息可以留作验收口径，或明确一个必要假设后继续。
- 用户提供调研、数据或现有文档时，先读与目标和数字有关的部分，区分实现事实、理论估算与待验证判断。不要为了写几条 OKR 全仓扫描或启动一轮技术调研。
- 跨多个组件的工作，先确认最终使用场景和各层作用；不要机械地给每一层各建一个 O，也不要擅自增加组件职责。
- 遵守用户要求的问答方式。少量关键问题集中提出，不把每个措辞选择都变成确认点。

## 2. 按结果组织，不按步骤凑数

- O 写要实现的业务或能力变化；KR 写证明变化发生的结果。常态 KPI 可以成为关键交付约束，但不要把所有日常指标搬进 OKR。避免只有“持续推进、完善体系、加强能力”等空泛表述。
- 每个 KR 保留具体对象、预期结果和必要验收条件。写完后暂时去掉“跟进、定位、对比、验证”等活动描述，检查是否仍能看出周期结束时交付什么、改善多少或支持什么决定；这是结果检查，不是禁用这些动词。探索中的方案或报告还应说明回答什么问题、供谁作出什么选择。
- 同一工作的验证、比较和决策可以合成一个 KR；记录、文档和发布流程通常并入对应交付结果。多个指标共同衡量同一交付或改善结果时可以合并，指标能分别测量不代表必须拆分 KR；具有独立交付或决策结果的工作保留独立 KR。
- 跨周期合并时，先检查各来源文档中每个 O 下的 KR 是否围绕同一成果主题，再确定合并结构和来源映射；不要机械沿用旧结构，也不要仅按「业务结果／工程能力」把同一主题拆散。用户要求与某阶段保持对应时，保持主题对应，不强求编号一致。
- 一个 O 只有一个 KR 时，检查它是否足以证明 O 达成。数量由实际结果决定；常见的三到五条是写作建议，不用拆步骤凑数，也不能为了少写而遗漏必要结果。
- 结合已知人力检查工作量；不能为满足模板而增加路线或任务，也不能擅自删掉用户明确要求的工作。

先区分承诺目标、挑战目标与探索任务，不必每条都显式贴标签。用户已经确认的类型不再问；类型会影响实际承诺且仍不清楚时，集中澄清。以下是写作场景，不是新增的 OKR 理论分类：

| 工作性质 | KR 应写什么 | 避免什么 |
| --- | --- | --- |
| 交付或改善 | 明确对象、通过条件或改善目标、必要质量约束；区分承诺与挑战 | 只有活动，没有可检查结果；把挑战目标说成已有把握 |
| 探索验证 | 验证对象、比较维度、证据及有依据的判断或选型结论 | 保证尚未验证的收益，同时保证质量不变 |
| 选型与采用 | 完成验证和结论；把收益门槛写成采用条件 | 把“完成选型”写成“必须找到达标替代品” |
| 持续跟进与维护 | 根据重要进展更新判断、选型或交付版本，保留验证依据与必要交付条件 | 要求同步所有更新，或只写持续关注 |

选型结论用符合用户语境的自然表述，写清判断依据与关键限制，不强制在正文枚举所有决策分支。有充分验证依据的“不采用”可以完成探索 KR；未测试、缺设备或关键证据不足不能伪装成已完成验证。

## 3. 数字有来源，比较有口径

- 区分四类数字：实测基线、理论估算、目标值、采用门槛。用户已确认的目标可以保留，但不能称为已实现的结果。
- 跨周期合并时，区分原定目标、实际成果与后续目标，保留指标适用的阶段、基线和范围；不要将前期已实现的收益重复计入后续提升目标，也不因合并或重组改变已确认的验收要求。
- 缺少依据时，不为了“更量化”随意填写百分比。用户需要建议目标时可给出明确标注的建议值及简短依据；只有目标大小影响实际承诺时才集中确认。
- 不把局部节省换成整体收益，不把理论上限写成必达目标。例如缓存减少不等于进程内存同比减少；节省资源也不能直接推出质量无损。
- 比较说明基准、指标方向和单位；必要时指出单次请求还是并发总量。沿用用户已理解的术语，能用“单个请求的速度（token/s）”消除歧义，就不必强改为“吞吐”。
- “至少一项改善、其余退化不超过……”必须能辨明比较指标集合。延迟／占用通常越低越好，速率通常越高越好；核对不等号，不改变用户确认的阈值。
- 质量、稳定性和无退化要求应能落到明确的用例、评价方法或基线。详细样本、统计方式、误差处理放在验收口径；不要凭空增加质量阈值或把有限测试结果说成无限保证。

## 4. 正文简洁，细节按需分开

默认格式：

```text
O1：要实现的变化
- KR1：结果名称。具体对象、结果和必要验收条件
- KR2：……
```

- 每条尽量一到两句。删除解释目标合理性的长段落，以及没有独立含义的“全面、有效、完善、可追溯”等词；需要保留时写清对象和结果。
- 默认不附排期、职责矩阵、长指标表或实施步骤。用户需要计划时另列；用户要求期限进入 KR 时保留。响应耗时等性能指标不属于排期，不应因此删掉。
- 核心成果指标保留在 KR 正文。多条 KR 共用的基线和测量规则，或单条 KR 较长的采用门槛，可按需放入“验收口径”并标明适用的 KR，保留完整条件。用户只要 O + KR 时，正文不附额外教程。
- 不因压缩而删除决定验收含义的条件，也不因消除抽象而塞入所有技术细节。

探索类措辞示例：

> 对比配置 A、B 的内存、速度和长上下文回答质量，形成采用 B 或保留 A 的结论。

这里承诺的是完成验证和作出有依据的决定，不预先承诺 B 同时省内存、提速且质量无损。示例技术和数字不作为其他任务的默认目标。

## 5. 修改与定稿

- 用户要求改一条：只修改该条和直接受影响的口径，不重写整份。修改文件前读取当前内容，以当前文件和用户本次要求为依据，不用对话中的旧稿覆盖用户手动修改。用户要求完整版本时才完整列出。
- KR 新增、删除、移动或重组后，按内容核对并同步已有合并说明、来源映射、验收口径和正文中的编号引用。区分目标文档编号与来源文档编号，不做全局编号替换；来源未变时保留来源编号，并修正「编号一致」等失效描述。
- 用户要求精简：合并重复步骤、删除解释，保留对象、结果、数字和约束。
- 用户要求 review：优先查目标冲突、不可验收的承诺、数字／单位歧义和重复 KR；只报告实际问题并给最小替换文本，不为展示工作量列出所有可能改进。
- 无实质问题就明确可以定稿。不要在定稿 review 时重新讨论已接受的目标、术语或排版。
- 起草和修改不授权执行其中的合并、发布、采购、消息发送或定时跟踪。

交付前自行检查一遍：是否保留了最新约束；每条是否有独立结果；全部 KR 是否足以支撑 O；数字是否越过证据；探索是否被写成保证成功；措辞是否具体且简短。修复实际问题后交付，不自动启动多轮评审。
