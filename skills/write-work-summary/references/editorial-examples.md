# 打磨案例与取舍

按遇到的写作问题选择对应案例：成果分组见第 1 节；动作与用途见第 2 节；用词和范围见第 3 节；指标比较见第 4 节；实践与评测见第 5 节；内容取舍见第 6 节。

案例包含历史材料的泛化与虚构演示，只用于说明判断方法。应用前核对当前项目是否具有案例中的事实和条件；不能把示例的主题、数字、术语或格式复制为新报告的要求。

## 1. 按成果分组，不为 OKR 凑章节

| 当前材料与阅读需要 | 可采用的组织方式 | 不应迁移的结论 |
| --- | --- | --- |
| 某 SDK 的接入与少量联调修复共同支撑项目试点 | 在接入成果下保留修复说明，一组成果对应接入与交付保障的两个 KR | 不是所有稳定性工作都应合并；有独立交付或重要影响时可以单列 |
| 运营人员负责活动报名和志愿者排班，没有 OKR，也没有前后统计 | 按两个工作主题写已形成并使用的报名规则、排班流程及各自用途 | 不补 O/KR 编号、效率提升比例，也不套用「架构、性能、工程实践」栏目 |
| 用户最新稿把完整 OKR 放在总体结论前 | 保留原顺序，成果标题就近关联 O/KR | 其他报告不必把 OKR 放在同一位置 |

合并章节时检查是否仍有实质内容支持关联的 KR；标题末尾多加一个编号不能补足成果。

## 2. 从动作落到能力或实际影响

只有材料已经支持右侧事实时，才可这样改写：

| 原表述 | 已知事实与更清楚的表达 |
| --- | --- |
| 将公开接口、运行环境和引擎实现分层 | 实际成果是多个 Runtime 可以同时存在并各自加载独立模型，就直接说明这项能力及会话、资源的隔离范围；不据此推导并行吞吐提升 |
| 优化表单编辑器的错误提示 | 若错误提示已能指出具体字段并保留当前输入，可写「标明填写错误的字段，用户修正后可继续提交」；没有保留输入的证据就不能添加这项承诺 |
| 完成采购资料整理 | 若已形成供应商材料清单和缺项反馈模板，并用于后续采购，可写清这两项产物及统一材料要求的用途；没有统计就不写节省了多少沟通时间 |

机制名称不足以说明问题影响。「模型转换问题」「索引问题」「表单校验问题」可能分别导致无法使用、结果错误或响应变慢，应查明真实症状，不能一律写成「提升质量」。

## 3. 动词与标题范围要与事实相称

「补齐导入与字段校验能力」可能把已有的导入功能也写成新增。若本期只是把原有导入接到新页面，而字段校验是新增，应分别写「支持已有导入能力」和「新增字段校验」。

若只修复了导出任务的异常提示，标题「全面提升平台稳定性」会扩大成果范围。可以直接以导出问题为题；若只是交付中的次要修复，也可并入对应交付成果。是否单列由实际影响决定。

调用方内部代号不影响归属时，可改用读者理解的角色，如外部合作方与内部运营；如果名称决定权限、能力或交付边界，仍需保留。不要默认所有项目都分成内部与外部两类。

## 4. 比较关系、数字和条件一起保留

「对比某日基线与某日新版」只提供版本身份。若材料确认变化是上游更新合并，应说明「合并前后」；若是实验组与对照组，则写明分组，不能改写成时间上的前后比较。

指标根据项目选择：

| 指标类型 | 报告需要保留的信息 |
| --- | --- |
| 批量导出耗时 | 已测得的当前耗时与改善幅度、数据量、运行环境及统计口径；仅有平均值时不能改成 P95 |
| 注册完成率 | 分子与分母含义、样本或分组范围、统计时段；区分百分点变化和相对提升，不能把比率变化称为系统性能提升 |
| 推理速度与窗口选择 | 已有的 decode、prefill 数据，以及模型、设备、配置和比较范围；这些条件只适用于相关性能评测 |

摘要给关键结果，正文给必要比较与条件，详细统计由已有报告承接。多个变更一起发布时，整体收益不能全部算作其中一个功能的贡献。没有量化数据的项目不需要建立指标章节。

## 5. 先确认实践的用途，再描述产物

发现的问题不能替代工作目的。即使都称为「评测」，也要先区分它帮助谁作什么判断：

| 已确认的定位 | 可以说明的用途 | 不能据此声称的结果 |
| --- | --- | --- |
| 接入真实业务前的模型精度基准 | 检查模型及推理引擎变更是否引入精度退化 | 不等于已经完成所有版本的无退化验证，也不自动等于业务效果优化 |
| 网站导航的可用性研究 | 为栏目分类与入口位置的选择提供依据 | 用户操作更方便不等于已经提高销售转化 |
| 财务数据导入前的核验流程 | 识别缺失字段与账目不一致，供负责人处理后再导入 | 形成检查流程不等于所有历史数据已经修正 |

「做过分析、发现问题」之后应说明用途；已经取得的结果仍按证据表述，不把目的写成完成状态。

产物按实际内容命名：有准备条件、操作步骤与判定标准时可称 SOP；回归用例描述具体检查；脚本负责执行；研究报告记录发现与结论。材料具备哪几项就写哪几项，不把它们相互替代，也不为凑工程实践而新增工具。

相似产物可能服务不同限制。历史模型服务案例中，手机服务使受限客户端能调用已适配模型，Mac 服务减少手机发热、占用对评测的阻塞。可迁移的是「分别解释用途」，其他项目无需具有这两类部署或同样的收益。

## 6. 保留重要范围，舍弃不影响判断的细节

一次总结曾删除需要大量背景才能解释的长上下文保护细节。这只能说明作者认为它不影响本期成果判断；不能推广为底层兼容性工作都不值得写。如果兼容性问题是项目能交付的关键，应保留解决的问题、适用范围与结果。

同样，「某月某日分别执行三次检查」可压缩为有证据的重复应用；关键交付月份、版本身份和试点范围仍可能需要保留。用户删去句末标点或使用中英混排，也不构成新项目的固定文风。
