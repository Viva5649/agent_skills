# 撰写与打磨工作总结

让不熟悉具体工作、但懂一些技术的负责人和 HRG 看懂：负责了什么，形成了什么成果，对项目或后续工作有什么作用。用户另有受众或模板时，以用户要求为准。

## 先确定当前稿与任务范围

- 优先读取用户最新文件，再使用会话中已确认的事实、完整 OKR、工作记录、指标和链接。修改前重新读取可能被用户手动编辑的目标段落，不用旧草稿覆盖新稿。
- 区分任务：要求起草或改写时直接完成授权范围的修改；只问含义或要求审阅时，先解释、指出问题并给替换建议。解释过程中发现新事实，不自动扩大成全文重写。
- 用户让你学习手工润色时，以最新文件为当前稿，即使其中的改动没有出现在会话里。对照可见版本，区分用户明确纠正、手工取舍和自己的推测；没有可靠前版时，只分析当前表达，不声称发现了逐字差异。不能仅凭措辞变得肯定，就认定完成状态发生了变化。
- 复用已确认的受众、主题、术语、格式与删除决定。仅对会改变成果归属、完成状态或数字含义的缺失信息追问；普通措辞自行判断。
- 没有 OKR 时仍可按主题整理成果，不编造 O/KR 编号。没有明确财年映射时，不根据自然月份推算 FY/Q 标题。

## 先厘清成果，再安排位置

用简短工作笔记把候选成果对应到「工作主题、交付对象、实际结果、用途、证据、O/KR、必要条件」。用途应回答成果服务哪个阶段、帮助判断什么或解除什么限制。笔记服务于写作，不默认另交一份表格。

- 从工作目的识别宏观主题，例如某项产品能力、客户服务或基础平台。不要把「架构、能力建设、缺陷修复」直接当成并列的工作主题；这些通常是同一主题内的贡献方式。
- 按成果实际服务的项目与发生阶段归类，不把后期平台建设塞回前期预研。相似技术动作可能服务不同交付：项目集成中的问题与组件内部能力可以分开，写清各自作用，避免重复计数。
- 有代码、有设计、有测试记录、有项目集成、有客户交付，是不同完成程度。不要把原型写成上线，把识别问题写成解决问题，把局部验证写成全面稳定，把交付准备写成商业化完成。
- 区分新增能力、已有能力的接入和原有能力的改进。「新增、补齐、首次实现」须有此前缺失的依据；描述接入后具备的能力可用「支持」，不要把原有功能写成新增成果。
- 原 OKR 表达的是目标。总结根据证据写已发生的结果，不能因为 KR 写了「零阻塞、无延期」就宣称已经达成。发现 KR 重复、边界混乱或不可验证时，另给简短修订建议，不擅自改写用户的历史承诺。
- 区分个人工作、团队工作和外部贡献。多项变化共同产生的结果，没有对照或其他归因证据时，不全部归因于其中一项个人改进。
- 证据阅读按问题收敛。普通文字整理不启动全仓审计、重跑实验或外部调研；只有具体事实不清时，再查直接相关记录或实现。证据不足就收窄表述或保留问题，不补写一个听起来合理的结果。

## 结构：总体结论、主题成果与完整 OKR

用户已有结构优先。成果正文按「总体结论 → 主题成果」展开，完整 OKR 独立成节供对照，保留用户选择的前置或后置位置。新稿没有顺序偏好时，可将 OKR 放在成果之后。主题数和成果数由内容决定：

1. **标题**：使用已确认的季度或阶段名称。正文不重复堆叠统计周期。
2. **总体结论**：按本期实际工作主题概括关键成果，从形成的能力、交付结果、效果变化或可复用实践中选择有证据的重点。不要求凑齐这些类别，也不要求每个主题都有量化结果。
3. **主题展开**：必要时用短段说明交付物的用途、服务对象和职责关系，让读者知道本人负责的范围。
4. **关键成果**：标题先写形成的能力或项目结果，有 OKR 时再就近标注对应编号。标题范围不能超过正文证据，例如修复局部异常不等于解决整个平台的稳定性问题。正文给少量能支撑标题的成果，不逐条复述 KR。
5. **本期 OKR（原文）**：用户提供完整 OKR 时，保留全部 O 和 KR，供未读过原目标的读者对照。原文保留目标措辞与承诺，只调整排版或补充对应编号，不改成已完成成果。用户明确不要附完整 OKR 或另有模板时遵从要求；缺少原文时不自行补造。

OKR 章节用于查阅原定目标，不重复成果或添加完成状态。核对成果引用的 O/KR 均能在原文中找到，补充编号时保持原有目标与 KR 的顺序。

一组成果可对应多个 KR，不要求一条 KR 一节。是否合并取决于结果是否独立：接入过程中的次要修复可并入接入成果，保留一句有事实依据的说明；有独立交付或重要影响时再单列。合并后核对 KR 对应的实质内容，不只追加编号；没有结果的 KR 不靠泛泛表述补齐。

重要落地月份可帮助读者判断进展。例行联调、评测、发布准备的多次应用，优先写应用对象、次数和作用，不逐次列日期；日期用于关键里程碑、识别比较版本或用户明确要求时保留。不要一律删除所有时间，也不要重建逐月流水账。

## 把工作动作写成读者能判断的成果

- 主句先交代形成的能力或解决的问题，再说明用途。抽象的架构分层应落到读者关心的能力与职责；内部模块或调用方名称不影响归属判断时，可按业务角色归类。具体范围可用短清单或括号补充，不把括号变成固定句式。
- 关键改善已有可靠解释、且有助于读者判断贡献时，用一句话说明关键做法如何影响结果。区分实测改善与机制解释；没有单项归因证据时，不将整体收益分摊给具体机制。
- 报告中的问题修复要说明实际影响，例如操作失败、结果错误或重复劳动。原材料只有机制名称时，先核实症状，不能统一改成「提升质量」。
- 同类事项按共同结果合并；影响不同对象、阶段或结果的事项分别说明。不要仅因都叫「修复」「建设」或「评测」就塞进同一条。
- 压缩到有意义的范围即可。不需要展示每个竞争时序、缓冲区机制和内部标识；也不要压成「完成核心集成」「加强保护」「提升工程质量」这类无法判断结果的词。
- 「完成测试、完成调研」等活动描述需要交代有证据的产物、发现或用途；活动本身是交付任务时，仍可作为成果，不编造后续业务收益。可复用实践本身是成果时，按实际产物命名：SOP 说明操作流程和判定标准，用例说明具体检查，脚本负责执行，不互相替代。
- 写评测应用前先确认定位。质量基准、业务效果评估和性能评测服务不同判断，不能从题集内容或发现的问题反推业务目的。「做过分析、发现问题」之后，要说明结果支持什么判断或取舍；用途与已验证结论分开，不能把「用于检查退化」写成「已保证无退化」。
- 允许舍弃次要事项。一个局部修复若需要大量背景才能解释，且不是关键成果、KR 的必要证据或重要限制，可留在详细记录中。总结无需覆盖全部提交；被用户删掉的事项，不因后来查清了机制就自动补回。
- 专业术语帮助理解时保留，使用当前项目的术语，不从案例引入无关的 SDK、Runtime 或模型概念。主题、交付物和依赖对象各用统一名称，不把不同对象合成同义词，也不强行翻译成熟术语。

需要具体改写示例，或用户反复指出「太细、太虚、重复、看不懂」时，读取 [打磨案例与取舍](references/editorial-examples.md) 中对应问题的部分。按写作问题选择案例，只迁移判断方法，不移植案例里的主题、事实、数字或栏目；没有适用案例时直接依据当前材料组织。

## 有量化结果时，分层呈现指标与条件

有可靠量化结果时应用以下规则。没有数据时，用已形成的能力、交付物、使用范围或已观察到的变化说明成果，不补造指标，不设置空白性能表。

- 总体结论优先呈现能判断现状的关键数值。材料提供当前水平时，不只展示改善比例；只有比例而没有基数时，不倒算未经证实的绝对值。
- 正文把关键比较放在最相关的成果中集中说明。摘要负责让人看到结果，正文负责支持比较，详细统计留给已有报告，避免多个 KR 重复同一份指标说明。
- 比较先说明对象之间的关系，例如「流程调整前后」「改版组与对照组」「合并前后」，日期或版本号用于定位。按指标类型保留必要的基线、样本、时间范围、统计方法和环境条件；性能实验可能需要设备与配置，业务比率可能需要分母与流量分组，不要求每个项目都列同一组条件。
- 单位、统计量、均值与区间、百分比与百分点的区别不能在压缩中丢失。推荐配置或方案须带适用范围，不推广为所有场景的最优选择。不同指标分别报告，不从速度改善推导质量或业务转化改善。必要限制紧邻对应结论，不为正文未声称的能力逐项添加缺数据说明；会改变成果判断的限制仍须保留。

## 迭代与交付

- 关键云文档就近链接到成果。准备写入云文档的正文优先保留用户提供的可分享链接，不夹带本地路径、仓库行号或内部证据清单。需要内部追溯时，沿用已有证据记录；不默认再生成一套旁路文档。
- 没有读取链接内容时，不假称已核对链接中的证据；用户要求保留链接不等于授权上传或发布。
- 局部要求只改目标及直接关联的位置。先检查用户最新稿，保留手工修改；用户撤回合并或纠正未做事项时，更新当前结论，不恢复旧版本中的错误。
- 学习用户的取舍原则，不机械模仿单个句式。可以提炼「同类能力合并后统一说明作用」「细节不抢主句」「边缘修复不强留」，不能推导为「所有细节进括号」「所有日期都删」或照抄偶然的标点、中英混排。更新规则时同步检查旧案例，避免保留用户已撤回的结构或定位；不把特定项目的选择变成所有报告的要求。
- 交付前检查：标题范围与成果是否相称、成果与 KR 的关系是否清楚、OKR 是否保留完整原文且编号对应、用途是否准确、是否重复认领、术语是否统一、数字和链接是否保留、动词与完成状态是否变强、次要机制是否仍挤占重点。
- 输出长篇报告时，使用可用的 `optimize-docs-readability` 与 `tech-doc-style-chinese` 做可读性和中文检查；未安装时自行检查上述项目，不因可选 skill 缺失而阻塞写作。检查不额外授权大范围改稿。
- 修改后读回并核对差异。用户要完整稿时，展示与文件一致的全文；局部修改时给文件链接和改后段落即可。
- 以已完成成果为主，不默认追加验收状态、当前待办、版本快照或下一步计划。确实影响成果解读的未完成状态和证据限制要保留；用户要求复盘或规划时，再按要求展开。
