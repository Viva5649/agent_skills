# Optimize Docs Readability

Reduce work a document makes its human Reader perform. In a writing task, use the
workflow below on the current draft. For a standalone readability review, report
findings and concrete rewrites without editing the reviewed files.

## Before delivering long-form writing

After drafting or substantially revising long-form text, perform one readability pass
before delivery, even when the user did not ask for one. The current authorized draft
is the target, including prose in chat or outside a repository; no filename or diff base
is needed. Ordinary short replies and the exclusions under Scope do not trigger this pass.

1. Establish Reader/Purpose from the writing request, then the draft's evidence in step 2.
   If evidence is insufficient, follow the existing stop condition rather than inventing it.
2. Apply the eight criteria in step 3 and correct supported findings directly in the
   current draft. This permits readability edits only within the existing writing task.
   Preserve factual meaning, citations, and necessary limits; do not fill missing facts or
   requirements through rewriting.
3. Perform step 5's evidence and information-preservation checks, then deliver the revised
   text in the original task's format. State any unresolved checks honestly. Do not load
   the report template or create a separate review report unless the user requests one.
   Do not restart the pass merely because it changed wording.

The report-only output and scope-selection rules below apply to standalone reviews.
A request only to review an existing document remains read-only.

## The single defect

**Reader-transferred work**: work a document forces its Reader to perform that its
author was in a position to perform instead.

Every criterion in this skill is one instance of it. Two rules follow, and they govern
every judgment you make:

- **No transferred work, no finding.** If you cannot state what the Reader is forced to
  do, discard the observation — however wrong the prose sounds to you. This is the only
  thing preventing this review from degrading into style nitpicking.
- **Intrinsic difficulty is not a defect.** Effort the Reader spends because the subject
  itself is hard does not count; the author had nowhere else to put that work. A
  document about distributed consensus is demanding because consensus is demanding.
  Report the missing signpost, not the difficulty.

A third rule bounds the first: "the Reader has to think" is not transferred work.
Use the source and Reader/Purpose to identify work the author could remove: recovering
information the author already held, filtering irrelevant wording, or deciding whether
repeated material adds a distinction. If information needed to understand the document
was never written down anywhere in the repository, that is a Documentation gap — hand it to
`audit-docs-landscape` and do not write it yourself.

## Scope

Standalone reviews cover a `README` at any level, Markdown under `docs/`, architecture
notes, onboarding guides, runbooks, ADRs, and repository-root design documents. The writing
workflow above also covers human-facing long-form drafts outside a repository.

For requirements, plans, specs, and design documents, review whether a Reader can
understand the writing. Leave requirement and design correctness, completeness, and
feasibility to `ce-doc-review`. The same document can receive both reviews for their
respective goals; passing a readability review does not validate the proposed solution.

Do not review:

| Excluded | Why | What to do instead |
| --- | --- | --- |
| Agent-directed files — **test by reader, not by filename** | Their reader is a model, not a human. Human reading criteria such as narrative flow and gradual build-up actively harm agent performance | Skip and say so. Include only if the user explicitly asks; then the Reader is "the person who maintains this instruction file", and no rewrite may change what the file instructs the model to do |
| Output regenerated by a script or template | Any rewrite is overwritten on the next generation | Report that the generator or template is the real subject, and stop. An editable prose draft the agent is writing is eligible for the writing workflow above |
| Code comments, docstrings, identifier names | Not repository documentation | Out of scope entirely |
| LICENSE and legal notices | Wording has legal consequence | Leave untouched |

**How to tell whether a file is Agent-directed.** The obvious cases are `AGENTS.md`,
`CLAUDE.md`, `SKILL.md`, and `.cursorrules`. But the test is who reads it, not what it is
called: **a document that an agent instruction file incorporates by reference as its own
rules is Agent-directed too**, whatever its name. Check what the repository's instruction
files point at before you classify a file as human documentation. If a file genuinely
serves both — instructions a model consumes and a human maintains — say so, treat the
maintainer as the Reader, and leave the instruction semantics alone.

## Standalone review output

Report findings and rewrites. Do not apply them. Apart from the review report and its output directory, do not
create, edit, move, or delete any file. The user decides which rewrites land; `codebase-documenter` applies them.

By default, save the full report to `.scratch/docs-review/<date>-readability-<target>.md`, relative
to the reviewed repository's root (or the workspace root when there is no Git repository).
Resolve that root from the review target, never from the skill installation directory or
a machine-specific path. Create the output directory if it does not exist.
Use `YYYY-MM-DD` for the date. For `<target>`, use `diff` when reviewing an explicit diff base, `multi-docs` for
multiple named documents, or the single document's filename without its extension.
Record the full selected file list and any diff base in the report.
Replace whitespace and filename-invalid characters (`/ \ : * ? " < > |`) in the name
with hyphens. If the path already exists, append `-2`, `-3`, etc. before `.md` rather
than overwrite it.
Return a brief summary and a link to the saved report in the conversation. Honor an
explicit output path or a request not to save. If saving fails, deliver the full report
in the conversation and state that it was not saved, with the reason.

## Process

### 1. Fix the review scope

Review exactly the documents the user named, or exactly what changed since an explicit
diff base:

```
git diff --name-only --diff-filter=d <base>...HEAD -- '*.md'
git diff --name-only --diff-filter=D <base>...HEAD -- '*.md'
```

The first command selects surviving paths; the second lists deletions to report as
skipped. Read only selected documents that still exist and are readable in the checkout;
report any unavailable path instead of inferring its Reader or rewriting absent content.
If none remain after filtering, report that there are no documents to review and stop.

If the user named neither documents nor a base, **stop and ask**. Never default to the
whole repository: that is `audit-docs-landscape`, and triggering it silently makes every
one-file review pay for a repository-wide scan.

### 2. Determine each document's Reader and Purpose

Do this before judging any content. Judging whether a passage belongs in a document is
only possible once you know who it is for and what they need to accomplish.

**Reader** is one class of human, defined by their situation and goal at the moment they
open the document — "someone deciding whether to adopt this project", not "backend
engineer".

**Purpose** is one of `TUTORIAL` (walk me through it), `HOW-TO` (complete this task),
`REFERENCE` (look up a fact), `EXPLANATION` (understand why).

Infer both from evidence, in this priority order, and record which source you used:

1. The user's explicit intent in the current task, including later clarifications.
2. The document's own statement — title, preamble, an explicit "this document is for…".
3. Its filename and location — `README.md`, `CONTRIBUTING.md`, `docs/adr/`.
4. Who links to it and in what words — the linking sentence usually states the
   Reader's situation directly.
5. The shape of the code it describes — an external contract implies a user, an
   internal mechanism implies a maintainer.

Use this evidence to establish which questions the document should answer and at what
depth. During iterative editing, identify what the user's correction changes: a readability
principle, a factual claim or evaluation scope, or a local presentation preference.
Apply a readability correction to equivalent occurrences within the authorized draft,
including other options, summary tables, detailed sections and the glossary; match the
underlying Reader loss, not just the same words. Keep facts and evaluation scope tied to
evidence, and preserve local preferences without turning them into universal writing rules.
This remains the current editing pass, not a new repository-wide review.

**When the evidence does not support a Reader, stop for that document.** Report "this
document does not identify its Reader" as the finding and do not proceed to
content-level criteria. Do not invent a plausible reader and review the remaining
content against it: that puts every later finding on a fabricated standard. A document
that cannot say who it is for has already shown you its root cause — Purpose confusion
is a symptom of that, not the disease.

You are guarding against your own bias here. You have read the surrounding code and
cannot un-know it, so gaps the real Reader would hit are invisible to you unless you
name that Reader first.

### 3. Apply the criteria

Each criterion is stated as the work it transfers. The right-hand column is the Reader
loss template for that criterion — a finding must instantiate it concretely.

Inspect sentences, paragraphs, and the whole document: a contrast split across sentences,
parallel examples, or the same closer after every section can transfer the same work.
Words, punctuation, and formatting locate candidates; dashes, triads, bold, and common
words alone do not establish a finding. Use context to establish Reader loss, without
inferring AI authorship. Do not flag quotations, proper names, or phrases being discussed
merely for matching a pattern.

| # | Criterion | Work the Reader is forced to do |
| --- | --- | --- |
| 1 | Reader and Purpose not identifiable | Decide for themselves whether this document is for them and what they get from it |
| 2 | Purpose confusion / unsuitable detail | Filter out content aimed at another Reader or an unnecessary level of detail |
| 3 | A term or project-invented mark is not explained where it first appears, or one referent has several names | Look the term up, guess, or work out whether two names mean the same thing |
| 4 | Point delayed or obscured by unnecessary wording | Read a whole paragraph to learn whether it is relevant, or extract the point from staging, repetition, and irrelevant contrasts |
| 5 | The actor is not recoverable | Infer who is supposed to perform the action |
| 6 | Dependency order broken / forward reference | Hold an undefined concept in mind and re-read once a later section defines it |
| 7 | Actionability gap | Reconstruct a missing step, prerequisite, or unstated assumption in an example — or recover a list the text replaced with a quantifier |
| 8 | In-document structure and navigation problems | Scan the whole document to locate the part they need, compare repeated passages for a distinction, or reconstruct relationships, including how technical mechanisms produce user-observable outcomes |

Execution notes where the criterion needs judgment:

**2 — Purpose confusion / unsuitable detail.** Symptoms: a full parameter table dropped
into a `TUTORIAL`; narrative explanation woven into a `REFERENCE`; a document that walks you through the
first half and becomes a lookup manual in the second. It matters because the reading
modes conflict — a `TUTORIAL` is read in order, a `REFERENCE` is scanned — so mixing
them penalises both Readers.

Also check depth against step 2's questions. An overview should preserve responsibilities,
relationships and necessary boundaries. Omit incidental implementation details or use a
verified pointer to an existing detailed reference when those details do not help answer
these questions. Information preservation means accurate claims and necessary distinctions,
not keeping every detail in every view. Keep conditions, evidence limits and identifiers
needed to interpret or use the claims in place; a link cannot replace necessary context.

**Boundary**: two Purposes that *must* coexist are not a defect. A design document has
to keep its rationale next to the rule that rationale justifies, and splitting them makes
both halves worse — that is Intrinsic difficulty.
There the correct output is criterion 8's reading path, marking which sections are read
in order and which are scanned. **Never recommend splitting the document.**

**3 — Unexplained terms, and inconsistent names.** Two failure modes; check both.

Before adding a definition, decide whether the Reader needs the term or mark. Remove
incidental modifiers or use a source-supported responsibility description when the
mechanism is irrelevant. Retain exact identifiers when lookup or meaningful distinctions
depend on them; do not merge distinct concepts merely to make names uniform.

A definition can exist and still leave the Reader guessing. Where needed for the current
question, explain the term's responsibility, when it is used, its relationship to nearby
concepts, and its scope. Distinguish a general concept from a product-specific format,
implementation or name. Expanding an acronym or calling several different tools an
"ecosystem" does not explain their roles. Do not require every definition to cover all
these details, add a glossary by default, or invent facts to complete one.

*Not explained.* This covers project-invented **marks** as much as words — numbering
schemes, abbreviations, labels, status codes. Separate three kinds.

- **Retained project-invented terms and marks** (internal code names, module nicknames, state
  names specific to this repository, custom numbering such as `#1`/`#2`) must always be
  explained on first use. For a numbering scheme, say what the numbers denote and what
  the ordering is: a Reader cannot tell an identifier from a rank, and a list deliberately
  not in numeric order makes the wrong reading the likelier one.
- **Industry-standard terms** (JWT, CI, DAG) depend on the Reader you determined in
  step 2. Without this split you will produce noise like "explain what HTTP is".
- **Terms that collide with a definition elsewhere in the repository** — the word is
  already defined somewhere in this repo with a different meaning. This is the most
  easily missed kind, and a one-line local gloss does not fix it: the document must state
  its relationship to the other definition, or the Reader will conflate two incompatible
  meanings. The better the Reader knows that other document, the more certainly they get
  it wrong. Before reporting a term as merely unexplained, grep the repository for it.

*One referent, several names.* The same thing is called two or three different things and
the Reader has to establish that they are one thing. This differs from the first mode: the
term was explained, what is missing is consistency. The fix is to fix one short form for
the concept and use it throughout, not to add another gloss at each site.

**4 — Point delayed or obscured by unnecessary wording.** Check whether the opening
establishes the topic and its relevance. Identify each sentence's role for this Reader:
facts, conditions, explanation, action, or navigation. Recommend cutting staged openers,
empty claims of importance, restatements of headings or preceding paragraphs, and
irrelevant accounts of the writing process when they serve none of those roles. Establish
what the Reader already knows from Reader/Purpose evidence; shared conversation context
alone does not justify removing background from a standalone document. Before retaining
or cutting an explanatory sentence, name the necessary fact, condition, interpretation
or navigation the Reader would lose without it. An explanation of the author's diligence
is not useful merely because it sounds cautious; a material evidence limit is useful.

Also check these patterns throughout the document, even when its conclusion is clear:

- "Not A, but B" / “不是 A，而是 B”: state B directly when the context has no A to correct.
- "A does not mean / show / imply B" / “是 A，不代表 B／不能说明 B／不能推导出 B”:
  state A directly when B is irrelevant to the Reader's current question.

Name the unnecessary comparison and the work it creates for this Reader. Remove the
negated material when the remaining statement preserves the facts, applicable conditions,
and distinctions the Reader needs. State the source-supported fact directly; do not
replace one unnecessary contrast with another negative construction.

**Boundary**: preserve evidence limits, scope restrictions, and corrections needed for
the current question. Prefer a positive statement of scope, such as
“本次测试仅覆盖单机吞吐量”, when the source supports it. Retain a contrast when a direct
statement cannot preserve the necessary distinction. Establish that need from the source, context, or
Reader/Purpose; do not invent a possible misconception to justify the detour. A negative
word alone is not a finding.

**5 — The actor is not recoverable.** The criterion is about the *missing actor*, not about
one sentence shape. Four mechanisms hide it:

- **Passive voice** — "the configuration is reloaded". Worth naming explicitly for its own
  reason: a passive sentence stays accurate and stays concise, so it is the easiest one to
  read straight past.
- **Elided subject** — "clean up temporary files afterwards", "retry on failure". In a
  Chinese-language document this, not the passive, is the dominant mechanism: technical
  Chinese rarely uses a passive marker and drops the subject as a matter of course. Review
  for the passive alone and you will systematically under-fire on such a document.
- **Nominalisation** — "after completion of validation": the action became a noun and the
  actor left with it.
- **Placeholder subject** — "the system retries", "the flow cleans up", "the relevant
  module validates it". The sentence is active and has a subject, but that subject is not
  any real component.

**The boundary matters as much as the criterion.** Subject-less sentences are everywhere,
so without a test this criterion floods the report. The test is **two or more candidate
actors**: report only where the Reader cannot settle on one actor from context. And where
the genre fixes the addressee, an imperative is not a defect — a `SKILL.md` or a runbook
speaks to the agent executing it or the person on call, so its actor is determined.

**6 — Dependency order.** Criterion 4 covers landing the point inside a paragraph; this
one covers concept order across the whole document. Symptoms: a section depends on a
term or state defined later; "we will cover this below" leaves the Reader carrying an
unresolved concept.

**Check this mechanically, not by attention.** For every project-invented term and mark,
compare where it first appears against where it is defined; a distance that crosses a
section boundary is a candidate, and you then judge whether the Reader actually needs the
concept in between. **Any rewrite that adds a definition must also re-check that term's
first appearance.** This rule was earned: a review of this repository's own design
document added a missing definition mid-document without checking that the term was
already in use two sections earlier, so the fix produced the next round's defect.

**Boundary**: genuinely mutually dependent concepts cannot be
linearised, and that is Intrinsic difficulty. There the correct finding is "add one
forward pointer to where this is defined", not "the order is wrong".

**7 — Actionability.** Check whether a Reader following this document gets through:
steps complete, prerequisites stated, examples self-consistent, and referenced files
and commands actually present. Two further checks:

- **Name the set; do not leave a quantifier standing in for it.** "the four design
  documents", "its two orchestrator documents" — a quantifier plus a type name with no
  list following it. The author knows which ones; the Reader has to list the directory to
  find out. Report it and supply the names in the rewrite.
- **Verify countable claims.** Counts, inventories, file sizes, versions asserted in the
  prose — actually check them against the repository rather than reading past them.

**Boundary**: existence, internal consistency, and countable claims only. Whether the
prose still describes what the code actually does is `neat-freak`'s job — do not audit
that here.

**8 — Structure, navigation, and visual explanation.** Check headings and reading paths.
Look for repeated openers, closers, or equivalent examples across sections that make the
Reader compare them for new information. Check whether generic labels, pervasive bold,
or decorative headings obscure priorities or make content harder to locate. Recommend
merging repetitions, simplifying labels, or changing headings while preserving distinct
items, useful scanning aids, and repetitions that serve a reading purpose.

For an overview, establish the whole before dependent detail. Put context needed to read
a visual before or beside it, and consolidate explanations that otherwise cause backtracking.
Choose numbering, legend placement and emphasis by when and how the Reader needs them,
not by turning one document's layout choices into universal rules.

Check grouping against a consistent organizing basis at each level. Business needs,
evaluation scope and implementation choices answer different questions; make those roles
clear rather than placing them under one misleading heading. For a glossary, keep entries
in the same category together unless a clear lookup scheme explains the order. Choose
categories by the distinctions the Reader needs, such as responsibility or deployment
stage; shared branding alone does not put a converter and a runtime in the same category.
Preserve a useful alphabetical or other lookup order; do not force every reference into
a tutorial sequence.

For comparisons, make the question behind each dimension explicit to yourself:

- Each option should answer the same question at comparable granularity. Separate
  independent dimensions when combining them hides distinct answers, such as model coverage
  and custom-model adaptation.
- Lead with the supported answer and necessary scope. A PR's status or conversion step is
  evidence, not a substitute for whether the requested capability is usable. Keep details
  in the evidence section when the summary does not need them to interpret the answer.
- Describe a restriction through its condition and effect: what cannot run, what is limited,
  or what the user must do. A generic dependency is not a meaningful restriction unless it
  excludes a relevant environment or creates a documented extra obligation.
- For relative advantages or disadvantages, identify the comparison and the material
  difference. A common maintenance cost can be relevant, but does not establish a relative
  disadvantage without evidence of a different burden.

Keep the document's agreed support criteria and necessary version, model, device or other
scope limits. Missing comparison evidence is a gap to report, not permission to invent a
ranking or turn "not verified" into "unsupported". This check concerns how the existing
evidence is presented, not an independent technical evaluation of the options.

Review existing visuals too. Color, border weight, grouping, position and arrows can imply
status, priority, containment, ownership or flow. Check those implications against the
source and legend; name any misleading inference rather than flagging decoration alone.
Use status marks consistently with the text; remove a mark when it merely repeats a
heading without helping scanning, or obscures a distinction. Do not prescribe a universal icon set.

Check whether dense prose makes the Reader reconstruct component relationships, branches,
state transitions, interaction order, or comparisons. Long paragraphs are a cue to
inspect, not a defect by themselves. Recommend a visual only when it reduces inference,
memory load, or rereading; use paragraph breaks, headings, or lists when those suffice.

| Information the Reader must reconstruct | Suitable representation |
| --- | --- |
| Components and their relationships | Architecture or relationship diagram |
| Branching steps or state transitions | Flowchart or state diagram |
| Interactions between actors over time | Sequence diagram |
| Options compared across dimensions | Table |

When recommending a new visual, identify the source passage, the relationships the Reader
must reconstruct, and the proposed representation. Put a paste-ready Mermaid diagram
or Markdown table in the Rewrite field, stating where to insert it or what it replaces.
Use only relationships supported by the source; preserve necessary explanatory text,
conditions, and exceptions. A decorative diagram or a duplicate of an already clear
explanation does not justify a finding. Organizing references within the selected document
is in scope; redesigning repository-wide navigation is not.

When the established Reader needs to understand or review feature behavior — for example,
a product manager assessing simultaneous article editing — also check whether the document
connects technical mechanisms to concrete scenarios, triggering conditions, observable
outcomes, and limits. Use the Reader evidence from step 2; never assume every document
serves a product manager. This remains criterion 8: the Reader has to derive product
meaning from mechanisms the author has already documented. Replacing jargon with simpler
words alone may leave that work unresolved.

Name the source information and the outcome this Reader must still infer, then provide
a scenario-based rewrite; use prose when it suffices. Preserve source-supported conditions,
results, and limits from the document or its referenced explanations. Do not invent product
promises or design rationale, or audit code to establish behavior. Necessary technical
detail in an API reference for developers is not a defect; an already clear explanation
in context needs no duplicate. Leave undocumented behavior unknown and follow the existing
gap and scope rules rather than treating a missing product decision as a wording problem.

For example, a source says the editor submits the revision it opened, and the article
service increments the revision after saving and rejects mismatches. A rewrite can say:
"If two people open the same article revision and one saves, the article service rejects
the other person's save because their changes use an older revision." Do not add a promise
that unsaved input is retained, or recovery steps, unless the source supports them.
Likewise, "many compiled artifacts to manage" leaves a deployment decision unstated.
If the source specifies a package's model, compiled context capacity and chip compatibility,
explain which changes require a new package. Do not infer one package per chip or promise
recompilation is always necessary when the source allows compatible reuse.

### 4. Draft the report

At this step, load [the report template](references/report-template.md) relative to
this skill directory and use it for the full report. Do not load it during evidence
collection. Keep the required sections even when there are no findings.

Open with the Reader and Purpose table — one row per document, with the evidence source
from step 2. This table is a primary deliverable: seeing "this document was trying to
serve two Readers at once" is worth more than ten rewrites.

Then group findings by document. Every finding has four fields, and is invalid without
all four:

| Field | Content |
| --- | --- |
| Location | `file:line`, or `file § heading` |
| Reader loss | What this Reader concretely forfeits: the sentence they cannot parse, the step where they get stuck, the concept they must hold unresolved, the wrong expectation they form. "Unclear phrasing" is not a Reader loss |
| Criterion | Which numbered criterion it instantiates |
| Rewrite | Replacement text they can paste in, **in the document's own language** — Chinese rewrites for a Chinese document, English for an English one |

Build each rewrite around the source paragraph's supported point. Rewrite the relevant
paragraph when phrase substitutions still leave it roundabout. Preserve project terms
and the author's voice where appropriate to Reader/Purpose, without inventing details
to make the prose sound natural. Apply criterion 2 when selecting detail; sentence-shape
preferences alone do not justify dropping facts. Step 5 checks information preservation
and whether the original difficulty remains.

Do not rank findings by severity. Documentation edits are cheap, so the only filter is
the defect definition itself: no nameable transferred work, no finding.

Close with a section listing **every criterion that produced no findings, and why**.
This section is not optional. Findings alone cannot tell the reader whether a criterion
was applied and passed or silently skipped, and a criterion worded too broadly or too
narrowly is discoverable in no other way. State briefly which criterion, and whether it
found nothing, was intercepted by the Intrinsic difficulty exclusion, or did not apply to
this Purpose.

Both review rounds run against this repository's own design document produced their most
useful conclusion here rather than in the findings — one falsified a prediction about
criterion 2, the other exposed that criteria 1, 2 and 4 had produced nothing twice
running. Do not drop this section as redundant.

### 5. Verify evidence and deliver

Before saving or delivering the report, the reviewing agent performs one evidence
verification pass. Check the source documents, not just the draft's wording:

- For each finding, verify its location and Reader evidence, then check whether the
  surrounding text or a referenced explanation already resolves the claimed difficulty.
- Compare each rewrite with the original for additions and omissions: facts, names,
  numbers, dates, citations, rankings, timing, conditions, certainty, and actor
  responsibilities. Do not turn "may" into "will", association into causation, or
  unverified information into a claim of absence. Judge omissions under criterion 2;
  ensure the remaining claims retain their scope, evidence strength and necessary limits.
  Re-check first appearances when adding definitions.
- Read rewrites in paragraph and document context for the original Reader loss under
  different wording, especially unnecessary contrasts, repeated closers, equivalent
  examples, and empty labels. Fix remaining difficulty within this verification pass.
- Reconcile repeated claims within the authorized draft: summary cells, detailed sections,
  glossary definitions and examples must agree on names, support status, scope and conditions.
  Check equivalent options affected by user feedback, not only the cited cell. Keep useful
  differences in detail; do not copy the full explanation into every location. In a
  standalone review, report inconsistencies rather than editing them.
- For a proposed or revised diagram or table, trace every node, connection, condition,
  sequence and comparison entry to the source. Remove invented or misleading relationships.
- Inspect the actual view for visual findings; supplied screenshots can establish review
  evidence. After changes to layout, connectors or emphasis, inspect a fresh rendering of
  the affected view in its intended format. Check arrow attachment and direction, clipped
  or overlapping labels, grouping and legibility. For Markdown formatting defects, check
  the target preview's actual headings, tables, emphasis, inline code and status marks as
  affected. For example, `**标签：**正文` may fail to render as intended; moving punctuation
  outside the emphasis is one possible repair, which still needs preview verification.
  Syntax validity alone is not visual verification; report unavailable rendering as
  unverified. A wording edit does not require unrelated visual checks.
- When the task identifies multiple maintained formats, such as HTML and Markdown, compare
  the edited headings, order, terminology, references and visual meaning across in-scope
  versions. Synchronize authorized versions in writing mode; report divergence in review
  mode. Allow useful format-specific layouts; do not require pixel-identical output or
  discover and edit unrelated copies.
- Account for all eight criteria per reviewed document, including no-finding outcomes
  and stopped checks. An unperformed check is not a pass, even in a report with no findings.

Remove false positives and correct unsupported conclusions or rewrites. If evidence
cannot be checked, move the affected claim to unverified coverage rather than present it
as a confirmed finding. Verify any corrected finding against its evidence before retaining it.
Record the verification method, evidence checked, corrections made (or none), and remaining
unverified items in the template. Then save and deliver under the output rules above.
This is self-verification, not independent review or a guarantee that nothing was missed.
Do not add a second reviewer by default.

## What not to change

- Licences and legal notices — wording has legal consequence, not a readability
  question.
- Externally fixed formats — changelog conventions, issue templates, badge syntax, and
  anything else consumed by an external tool or community convention.
- **Repetition with a reading purpose** — preserve useful navigation, summaries,
  teaching repetition, and safety notices, including destructive-operation warnings.
  Each sentence needs a useful role; it need not add a new fact.
- **Evidence and limits that affect interpretation** — preserve research methods,
  sources, time ranges, evidence limits, and genuine uncertainty. Distinguish these
  from irrelevant narration of the writing process.
- Other people's attribution and acknowledgements.
- Pure taste. If you cannot say which version leaves the Reader better off, say nothing.

## Stop conditions

- **Scope undetermined** — no named documents, diff base, or current writing draft. Ask; do not guess.
- **Subject is regenerated by a script or template** — report that the generator or template is the real subject,
  and stop.
- **Subject is an Agent-directed file** and the user did not explicitly ask for it —
  report that you skipped it and why.
