# 编写可评审的技术方案

产出措辞严谨、可扫读、能指导后续工作的方案。让跨岗位读者理解业务用途、技术选择、本期变化和验收依据；让实施者找到具体职责、设计条件和详细资料。

## 1. 从当前进度进入

先读用户指定文档、已确认结论、进度记录及目标仓库约定。已有结论继续使用，局部修改只处理受影响的内容。

| 当前任务 | 本轮产出 |
| --- | --- |
| 需求很大，尚未成稿 | 确定范围、文档分工和首个专题，写出有依据的内容，集中列出会影响方案的待决策项 |
| 正在打磨某节或专题 | 修改指定内容，并同步受影响的总览、专题和图稿 |
| 要求先分析或给结构建议 | 给出问题、建议结构及内容去向，保留原稿，等待用户确认重组 |
| 已授权重组、合并或替换 | 执行内容迁移、引用修复和遗漏核对，再替换维护入口 |

明确这五项输入：读者及评审目的、负责的模块边界、本期交付状态、已有资料、输出位置与载体。先从上下文取得答案，只询问会改变范围、目标、责任或验收的问题。写作输入用于选择内容与结构，正文只保留读者判断方案所需的背景，不逐项交代写作安排。

基础设施可以从上层总需求、现有消费方和已确认任务提取需求，不要求额外编造一份独立产品需求文档。时间未确定时沿用「本期」，按交付物和依赖安排阶段。用户已暂缓的方向只在必要处保留演进说明。

长期打磨时，在项目已有记录中保存「问题、明确结论、依据、影响文件、下一步」。记录当前有效决定；历史决定按项目归档方式保留。用连续编号提问，选项要写清区别和推荐理由，不让用户重新确认已经回答的问题。

## 2. 分清现状、设计与证据

按任务需要查阅架构文档、相关调用路径、接口、配置、实验报告和用户提供的资料。核对绑定的子仓库及实际版本，避免把独立 checkout 的内容当作当前依赖。

| 信息类型 | 依据 | 写法 |
| --- | --- | --- |
| 当前实现 | 代码、配置、现行契约及实际验证 | 说明已实现到哪一层、哪些消费方已接入 |
| 本期目标设计 | 用户已确认需求及设计决定 | 明确本期要改变的行为、负责模块和完成结果 |
| 候选措施 | 调研、原理分析、尚未完成的对照 | 写明预期作用与验证条件，收益保留为待验证 |
| 待补输入 | 缺少数据、阈值、依赖或设计决定 | 用 ⚠️ 标记具体缺口，放入对应内容及待补汇总 |

代码用来确认当前实现，目标行为按已确认需求描述。实现与目标冲突时分别记录，不能悄悄把目标改回现状，也不能把计划写成已实现。测试服务、临时接入和已打通的工程链路按实际用途表述。用户确认的外部平台能力可以作为有来源的输入；仓库没有材料时，注明尚缺哪项证据。

先自行调查事实问题，再问设计选择。数据报告中出现过的数字，需确认适用条件和是否被接受为目标；不要据此新增 SLA、质量门槛或业务承诺。新增方案可以提出建议，但在用户确认前保留建议状态。

## 3. 确定文档分工

方案文档只拆一层：总览 → 专题。专题承接某个细分方向，有独立的技术决策、验证方法或维护需求时才单独成文，短主题留在总览即可。更细内容通过专题内的章节或引用既有技术文档承接，不再拆出子专题。

| 文档 | 应回答的问题 |
| --- | --- |
| 总览 | 模块处于整体方案哪里、服务谁、提供什么、本期改什么、为何这样选、目前表现如何、如何验收 |
| 详细专题 | 针对什么差距做哪些改动、各层如何配合、必要失败处理是什么、验证如何执行 |
| 既有技术文档 | 当前接口、架构、配置、机制及操作规程的权威定义 |
| 决策和进度记录 | 已确认什么、尚缺什么、哪些文件要同步、下一步做什么 |

默认总览采用产品／场景视角，专题采用工程／技术视角。逐篇根据主要需要评审的决定选择视角：

| 写作视角 | 主要评审问题 | 组织主线 |
| --- | --- | --- |
| 产品／场景 | 服务谁、完成什么、本期改善什么、如何判断效果 | 场景、能力、当前表现、本期工作、验收 |
| 工程／技术 | 技术路线是否合理、模块如何配合、实现条件是否充分 | 架构、职责、机制与接口、技术取舍、验证 |

总览和专题都可选用任一视角，也可以组合为工程总览与场景专题。每篇围绕主要评审问题组织内容；专题采用场景视角时，仍需保留指导实施的技术设计。

当多个主题尚未成熟时，先搭简短总览，选一个需求与证据较充分的专题打磨，再把结构用于其他主题。复用的是需要回答的问题，技术章节随主题变化。创建或重组结构时读 [结构选用与表格示例](references/document-shapes.md)。模板目录中的可选章节统一标注「（可选）」并说明保留条件，成稿按实际内容保留或省略。

采用产品／场景视角时，业务用途、能力与当前表现、本期工作、质量与验收放在同一个场景下。多个场景共用技术方案、基线和验收时，可以合并小节或用共用表说明，保留各自的业务差异。模型交付、资源共存、观测等跨场景机制集中维护。共用机制的场景差异要就近可见。

首次系统评审可以先说明现有架构及能力，再在各场景和机制下标出本期新增内容。总览保留影响选型、收益、边界和采用条件的细节；完整参数、接口字段和基础功能检查放入已有技术文档或专题。

## 4. 把技术工作连接到业务用途

每个场景写清消费方、业务行为、调用能力、返回结果及其用途。场景、能力、模型、组件和进程分别表达，避免把不同维度混成同一分类。多个业务场景可以共享同一种技术能力。

明确业务方和基础设施各自负责什么。业务方的数据管理、索引或产品交互可以作为背景和依赖，不自动列为基础设施本期工作。只列已确定的消费方。渠道说明区分进程内调用、内部跨进程接口和对外接口。

核心技术方案说明「哪个模块在什么条件下对什么对象做什么，产生什么结果」。生命周期按加载、复用、释放、恢复组织，保留发起者、关键条件、资源归属和失败后的行为。不同场景规则明显不同时分别展开，概览可用同一张表比较。复杂实现时序交给专题。

选型比较使用一致维度，每个候选先写影响采用的主要因素，再保留必要限制。采用依据、未验证项和不支持项分别表达。

优化措施至少连接到具体指标或阶段，例如 prefill、decode、内存。总览可保留措施、优先级、预期收益和关键条件；专题展开参数、成本、风险及实验顺序。研究中的措施保留不确定性，验证后再更新采用结论。

## 5. 把数据与验收写准确

优先复用适用的正式基线。选取较新报告前，核对设备、版本、输入、配置与测量范围，避免不同口径拼成一组结果。没有测量的指标标为待补，不写零、不猜值。

- 性能表选择能判断当前能力与本期目标的核心指标；不同输入类型保留有代表性的规模，完整档位留在报告。设备、单位及影响解释的口径就近可见。
- 将实测值、估算值、理论收益和目标分开。均值、峰值、上下限和不同内存统计项保持原义。必要口径用表后的 `> **内存口径：** …` 等说明，避免塞满单元格。
- 数值目标保留比较符号和边界。区分相对变化与百分点；由比例换算绝对值时记录公式、基数与精度，不改变原约束。
- 质量验收写明评测集、对照对象、指标、通过条件和准备状态。模型输出、人工标注、业务相关性判断按真实来源命名。工程链路已通的方案只有在获得认可后才用作质量基线。
- 业务评测集与通用公开评测集分别说明用途。未就绪的数据、评分规则或质量门槛，在场景与交付依赖中保持同一状态。
- 运行观测连接「指标」与「用来判断什么」。单次诊断说明查询入口、关联字段和能查看的信息；完整埋点字段及统计细节引用已有文档。

验收选择能证明本期目标的证据。总览突出核心能力、收益、平台约束和关键失败结果，常规功能检查留在详细验证资料中。未来目标只列有本期变更且已确认的部分。

## 6. 用图表减少读者推导

架构、关系、关键交互与状态变化用图；职责、对比、参数、进度和验收用表；结论与必要解释用短段落。图要呈现关系或过程，避免只把段落放进多个框。

先为每张图定义它要回答的问题、参与者、关键关系与适用状态。复杂度允许时用总图，差异大时按场景拆图。优先检查已有图是否可复用；引用前核对内容仍符合当前方案。

总览图放在所属章节前部，局部图紧邻对应机制。图前放必要前提或结论，图后用表格补充图中无法清楚表达的维度。概念在首次使用附近解释；共享条件放在表前，统计或字段说明放在相关图表后，并用引用块区分正文。不要逐项复述图表。

图片尚未制作时，按仓库格式留占位，注明图号、图名、要表达的关系及已有源文件。采用章节编号时，如图 `1-1`、图 `2-1-1`。需要正式制图再调用 `create-system-diagram`；配色、线型、坐标和渲染检查由绘图 skill 维护。

表格一列表达一个独立维度，同行维持可比性。长单元格先判断是否属于总览，再精简表达；必要时拆表或移入专题，保留关键条件。表格末尾不加句号。标题直接命名主题，省去「下表说明」「核心方案如下」等重复引导语。

## 7. 持续修改与新旧稿收敛

按用户当前审阅范围推进。关键决定改变后，同步受影响的正文、表格、图示文字、专题、待补项和引用。局部改词不触发整套方案重写，也不恢复用户已删除或暂缓的内容。

重大结构调整先保留原稿，用副本承接新结构和图示占位；用户批准替换后再收敛。处理新旧稿时读 [内容迁移与一致性检查](references/content-retention.md)。核对具体信息的归宿，确认工程细节已有文档承接后，再移除并行副本。

默认让总览和专题各维护自己的内容职责。两份仅结构不同的总览会增加同步成本，优先保留一个维护入口；只有读者与用途确实不同、内容职责清楚时才长期保留两份。

## 8. 交付前核对

先按方案内容检查，再做文风和排版检查：

1. 读者能看出谁使用、做什么、当前状态、本期变化及如何验收，主要阅读顺序符合本篇的评审重点。
2. 当前实现、目标设计、候选措施和待补项一致；职责、前置条件及必要失败处理有依据。
3. 性能与质量数据可追溯，量纲、统计对象、比较方式和目标没有在精简中改变。
4. 总览、专题和图稿中的同一决定一致；技术细节移出后有有效归宿。
5. 文件引用、章节锚点、图号和子仓库路径有效。用户要复制到云文档时，可将来源集中到文末「参考依据」表，注明支撑内容，正文保留必要条件。
6. 中文文案按 `tech-doc-style-chinese` 处理；长篇人类读者文档按 `optimize-docs-readability` 复看。只在实际需要时读取并应用这些技能，沿用用户已确认术语。

跨岗位试读可用时用于验证理解；无法安排时，根据读者任务复看，并明确实际检查范围。交付文件、关键改动、尚缺的输入和已完成检查。文档完成状态与方案实现状态分别报告。
